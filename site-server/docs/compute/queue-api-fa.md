# صفِ ماندگارِ سرورِ پردازش — راهنمای برنامه‌نویس (برای عامل‌های ادیتور)

خواستهٔ مالک: «اگر چیزی زده شد که پردازشش برود آن‌ور و آنلاین نبود، منتظرش بماند و هر وقت وصل شد انجام دهد؛ ناموفق نشود مگر ارور بدهد یا لغو شود.»

این سند فقط می‌گوید **چطور از صف استفاده کنید**. چرایی و فهرستِ مسیرها در `queue-audit-fa.md` است.

## قاعده‌های تازهٔ هستهٔ صف (`apps/compute/services.py`)

| موضوع | قبلاً | حالا |
|---|---|---|
| قطعِ گره وسطِ کار (lease تمام شد و **گره خاموش است**) | کار به صف برمی‌گشت ولی یک «تلاش» می‌سوخت؛ بعد از دو بار `FAILED` | به صف برمی‌گردد و **تلاش نمی‌سوزد** (`lost_count` بالا می‌رود). پس از `MAX_LOST_FREE=8` بار پشتِ‌سرهم، قطع‌ها هم تلاش حساب می‌شوند (تا کاری که هر بار عامل را می‌کُشد حلقهٔ بی‌پایان نسازد) |
| کارِ ساکت روی گرهٔ **زنده** (گیرکرده) | تلاش می‌سوخت | همان (تلاش می‌سوزد) |
| خطای واقعیِ کار (`finish(ok=False)`) | تا `max_attempts` تلاش | همان |
| ماندن در صف | بدون سقف (فقط `wait()` سقف داشت) | بدون سقف؛ سقفِ اختیاری: `ComputeJob.max_wait_s` یا «سقفِ انتظارِ کارها» در تنظیماتِ سرورهای پردازش (پیش‌فرض ۰ = هرگز) |
| لغو | فقط صف‌شده | هر لحظه؛ اگر گرهِ کار خاموش است همان لحظه، وگرنه با `progress` ِ بعدی |
| `progress` برای کارِ پایان‌یافته | ردیف را دست می‌زد | دست نمی‌زند و `{"cancel": true}` برمی‌گرداند اگر لغو شده |

## ثبت کار

```python
from apps.compute import services as compute

# ۱) ثبتِ ماندگار — به‌جای enqueue(..., require_online=True) وقتی کاربر منتظر نمی‌ماند و خودتان job.uid را نگه می‌دارید
job = compute.enqueue_durable("photo.edit", payload, files, store=store, origin="photoedit", priority=95)
# فقط اگر هیچ گرهٔ فعالی با آن توانایی «اصلاً ثبت نشده» ComputeUnavailable می‌دهد.
# job.message = «در صف — منتظرِ روشن شدنِ سرورِ پردازش» (اگر گره‌ای آنلاین نباشد)

# ۲) قدیمی: enqueue(...) با require_online=True ⇒ اگر هیچ گره‌ای آنلاین نیست فوراً ComputeUnavailable (برای پیش‌نمایش‌های تعاملی)
```

پارامترهای تازهٔ `enqueue`: `not_before=` (شروعِ زمان‌بندی‌شده)، `window="02:00-07:00"` (فقط در بازهٔ وقتِ تهران گرفته می‌شود)، `category="download"`، `max_wait_s=`، `lease_s=`، `max_attempts=`.

## منتظر ماندن برای نتیجه

```python
job = compute.wait(job, timeout_s=900, patient=True, park_after_s=120)
```

* `patient=True`: ماندن در صف هیچ‌وقت کار را لغو نمی‌کند (ساعتِ «مهلتِ اجرا» فقط از لحظهٔ گرفته‌شدنِ فعلی می‌شمارد و اگر کار به صف برگردد از نو شروع می‌شود). فقط خطای واقعی، لغو، یا «بیش از مهلتِ اجرا روی گرهٔ زنده» آن را می‌بُرد.
* `park_after_s=120`: اگر کار در صف مانده و **هیچ گرهٔ توانایی آنلاین نیست** و ۱۲۰ ثانیه گذشت، کارِ ComputeJob لغو و `compute.NodeWaiting` داده می‌شود (نخِ Celery اشغال نمی‌ماند؛ ما فقط ۴ نخ داریم).
* بدونِ `patient` رفتارِ قدیمی (سقفِ `2×مهلت+۶۰` ثانیه و لغو).

## کارِ Celery که نباید شکست بخورد (پارک)

کارِ کاربر (ردیفِ `apps.jobs.Job`) وقتی خطایی بخورد که **نشانهٔ `node_waiting`** داشته باشد، در `Job.mark_failed` به‌جای «ناموفق» **پارک** می‌شود (`apps/compute/park.py`):

1. ردیفِ Job می‌شود `QUEUED` با برچسبِ «در صف — منتظرِ روشن شدنِ سرورِ پردازش» و ریپرِ کارهای مرده آن را نمی‌کُشد؛
2. یک «کارِ منتظر» (`ComputeJob(kind="wait.node")`) ساخته می‌شود تا در «صفِ پردازش» دیده، شمرده و لغو شود؛
3. نخِ Celery آزاد می‌شود؛ هر دقیقه `wake_parked` (در `compute-maintenance`) می‌بیند سرورِ توانا آنلاین شده یا نه و **همان تسک را با همان آرگومان‌ها** دوباره می‌فرستد.

چطور خطا را «منتظرِ سرور» کنیم:

```python
raise compute.NodeWaiting("پیام", "ffmpeg")      # قابلیتِ لازم: comfyui / ollama / voice / photo / video / ffmpeg
# یا روی خطای خودتان:  err.node_waiting = "voice"
```

یا **دروازه** در ابتدای تسک (پیش از کارِ گران):

```python
from apps.compute import park
job = Job.objects.get(id=job_id)
if park.gate(job, "ffmpeg"):       # سرورِ توانا آنلاین نیست و چنین سروری ثبت است ⇒ پارک شد
    return {"waiting": "node"}
```

نکته‌ها:
* پارک فقط وقتی کار می‌کند که تسک زیرِ Celery واقعی (نه eager) و با `Job` ِ خودش اجرا شود، و **سرورِ ثبت‌شده‌ای با آن توانایی باشد**؛ وگرنه مثلِ قبل «ناموفق».
* چون تسک از اول دوباره اجرا می‌شود، گیتِ ابتدای تسک ارزان‌تر از پارکِ نیمه‌کاره است. هزینه‌ای که پیش از خطا رزرو شده (`billing.reserve`) را قبل از `mark_failed` آزاد کنید (مثلِ `generate_image_task`).
* فراخوانی که `Job` ندارد (چتِ مشتری، HTTP) همان `AllProvidersFailed`/`ComfyUIUnavailable` را مثلِ قبل می‌بیند.

## هوشِ مصنوعیِ تعاملی (`services/ai/routing.py`)

وقتی مسیرِ لوکال (سرورِ پردازش) **خاموش** است و متیس هم جواب نمی‌دهد (مثلاً ۴۰۲) و سروری با `ollama` ثبت است، `AllProvidersFailed` نشانهٔ `node_waiting="ollama"` می‌گیرد؛ پس هر تسکِ `Job`‌دار که `job.mark_failed(exc)` را با همان استثنا صدا بزند پارک می‌شود. پیام‌های خطا برای فراخوان‌های بی‌Job عوض نشده‌اند.

## نمایشِ وضعیت به کاربر

* `GET /api/v1/compute/queue/` (کارکنان) و `.../queue/summary/` برای نوار بالای پنل.
* برای صفحه‌های خودتان: `from apps.compute import queue as QV; QV.one(job)` ⇒ `status_text` فارسی («در صف — منتظرِ روشن شدنِ سرورِ پردازش»، «در صف — نفرِ ۲ام»، «در حال پردازش روی «gpu-1» — ۴۰٪»، …)، `position`، `waiting_s`، `can_cancel`.

## قفلِ SQLite (database is locked) — اگر ثبتِ کار می‌کنید

سایت روی SQLite است و هم‌زمان فقط یک نفر می‌نویسد. از این دور:

* تنظیمات (`config/settings.py`): `busy_timeout` سی‌ثانیه، WAL، و `transaction_mode=IMMEDIATE` (داخلِ `atomic()` اول قفلِ نوشتن گرفته می‌شود و صبر می‌کند؛ «خواندن ⇒ نوشتن» وسطِ راه خطای فوری نمی‌دهد).
* `apps/compute/dbretry.py`: `call_with_retry(fn, ...)` و دکوراتورِ `@retry_on_lock` — روی «database is locked» با عقب‌نشینی دوباره تلاش می‌کنند؛ خطای دیگر را فوراً می‌دهند و **داخلِ `atomic()` تکرار نمی‌کنند** (تراکنش شکسته است؛ بیرونی‌ترین لایه تکرار می‌کند). اگر چند نوشتنِ پشتِ‌سرهم دارید، هر کدام را جدا (یا کلِ ناحیه را در یک تابعِ idempotent) بپیچید.
* `compute.enqueue*` ورودی‌ها را اول کپی می‌کند و ردیف را با **یک** `INSERT` می‌سازد؛ کارِ نیمه‌ساخته (بی‌`inputs`) دیگر پیش نمی‌آید. اگر ساخت شکست بخورد پوشهٔ ورودی‌ها هم پاک می‌شود.
* `apps.jobs.Job.save` خودش روی قفل تکرار می‌کند (وضعیتِ تسک‌های Celery).
* نماهای گره (`node_api`) اگر پس از همهٔ تکرارها هم قفل بود «۵۰۳ + Retry-After: 5» می‌دهند؛ عاملِ ۲٫۶ این را تکرارپذیر می‌داند.
* بیدارکردنِ کارهای پارک‌شده دسته‌ای است (`NM_COMPUTE_WAKE_BATCH`، پیش‌فرض ۸ در دقیقه).
* آزمونِ فشار (روی **کپی**، نه سایتِ زنده): `/root/compute-r1-stress.py`.
