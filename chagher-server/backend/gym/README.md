# سیستم مدیریت باشگاه (Gym)

بک‌اند Django/DRF برای یک SaaS مدیریت باشگاه: مربی با **شماره تلفن** ثبت‌نام می‌کند، **توکن** می‌خرد و با **هوش مصنوعی** برای مشتری‌هایش برنامه ورزشی و غذایی شخصی‌سازی‌شده (با فرهنگ غذایی ایرانی) تولید می‌کند و خروجی **PDF** می‌گیرد.

## امکانات اصلی

- **دو مدل کسب‌وکار در یک سامانه**
  - **B2B (باشگاه):** مربی ثبت‌نام می‌کند، تجهیزات و غذاهای باشگاهش را تعریف می‌کند و برای ورزشکارانش کد دسترسی می‌سازد.
  - **B2C (کاربر شخصی):** هر کسی مستقل از باشگاه ثبت‌نام می‌کند، محیط تمرینش را انتخاب می‌کند (خانه بدون تجهیزات / خانه با دمبل و کش / باشگاه عمومی) و برای خودش برنامه می‌گیرد.
- **احراز هویت با شماره تلفن** — بدون username، با Token Authentication (DRF). لاگین برای هر سه نقش یکی است و پاسخ شامل `account_type` است. بازیابی رمز **دو مرحله‌ای با کد OTP پیامکی** است (۴ رقمی، اعتبار ۱۰ دقیقه، حداکثر ۵ تلاش) و endpoint های حساس (ورود، بازیابی رمز، کد دسترسی) **rate-limit** دارند.
- **تولید برنامه با AI** — از طریق هر API سازگار با OpenAI (پیش‌فرض metisai.ir)، تنظیم از پنل ادمین (`APIConfig`). با `program_type` مشخص می‌کنید فقط برنامه ورزشی، فقط غذایی یا هر دو تولید شود — بخش درخواست‌نشده اصلاً از مدل خواسته نمی‌شود.
- **اقتصاد توکنی** — هزینه بر اساس آنچه واقعاً می‌خواهید: ورزشی و غذایی با هم ۵۰ توکن، فقط ورزشی یا فقط غذایی ۲۵ توکن، ویرایش هم ۲۵ توکن؛ کیف پول مشترک مربی/برند باشگاه
- **مشتریان باشگاه** — کد دسترسی یکبارمصرف (تولید با مولد امن `secrets`؛ طول کد از پنل ادمین: **تنظیمات سامانه → طول کد دسترسی**، پیش‌فرض ۴ رقم، تا ۱۲ رقم) در **دو حالت: دائمی یا زمان‌دار** (مربی مدت اعتبار را به روز یا دقیقه تعیین می‌کند؛ کد منقضی نه فعال می‌شود و نه ورود مجدد می‌دهد)، رزرو توکن قبل از فعال‌سازی، درخواست توکن از مربی، و **بازگشت خودکار توکن رزروشده** اگر کد تا مهلت تعیین‌شده فعال نشود
- **شمارش معکوس کد دسترسی** — پاسخ ورود مشتری دو فیلد `access_code_is_permanent` و `access_code_remaining_seconds` دارد تا فرانت مثل تایمر کد پیامکی، زمان باقی‌مانده را ثانیه‌به‌ثانیه نشان بدهد (عدد از سرور می‌آید، نه از ساعت دستگاه کاربر)
- **دستورالعمل ثابت مربی** — متنی که در تولید هر برنامه‌ی باشگاه با اولویت بالا به هوش مصنوعی داده می‌شود
- **پیشنهاد هوشمند دستگاه و حرکات** — بر اساس محبوبیت در کل سامانه: هرچه دستگاهی را کاربران بیشتری ثبت کرده باشند بالاتر پیشنهاد می‌شود. مربی با یک کلیک گروهی به تجهیزات باشگاهش اضافه می‌کند و کاربر شخصی حرکات رایج محیط تمرینش را می‌بیند. تا وقتی داده واقعی کم است، کاتالوگ پایه (۴۰ حرکت) جای خالی را پر می‌کند.
- **کد تخفیف با کمیسیون** — سیستم افیلیت: سازنده کد از هر خرید درصد می‌گیرد
- **خروجی PDF** — با WeasyPrint و fallback خودکار به ReportLab (متن فارسی RTL). بالای هر صفحه دو لوگو می‌نشیند: لوگوی ثابت چغر و لوگوی همان باشگاه (از «برند باشگاه» خوانده می‌شود؛ کاربر شخصی فقط لوگوی ما را می‌گیرد). برنامه ورزشی ستونی است (هر ستون یک جلسه، حداکثر ۲ صفحه) و برنامه غذایی جدولی: هر روز یک کادر سرتاسری و هر وعده یک ردیف — نام وعده در ستون راست، اقلامش در ستون چپ (دو روز در هر صفحه، حداکثر ۴ صفحه).
- **برندسازی باشگاه** — لوگو، رنگ‌ها و مشخصات تماس
- **سایت معرفی** — صفحه اصلی، بلاگ، تماس، درباره ما + sitemap و robots.txt
- **مستندات API** — Swagger در `/api/docs/` و ReDoc در `/api/redoc/`

## راه‌اندازی

```bash
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser   # با شماره تلفن
python manage.py runserver
```

سپس از پنل ادمین (`/admin/`):
1. یک رکورد **تنظیمات API** بسازید (کلید API هوش مصنوعی)
2. یک **بسته توکن** فعال تعریف کنید

> **ویندوز:** اگر کتابخانه‌های GTK نصب نباشد WeasyPrint کار نمی‌کند و تولید PDF به صورت خودکار با ReportLab انجام می‌شود.

## نقش‌های کاربری

هر کاربر دقیقاً یک `account_type` دارد و فقط به مسیر خودش دسترسی دارد:

| نقش | چطور ساخته می‌شود | دسترسی اختصاصی |
|---|---|---|
| `coach` | `POST /api/auth/register/` | تجهیزات، غذاها، برند باشگاه، مدیریت مشتریان |
| `gym_client` | خودکار، هنگام ورود با کد دسترسی باشگاه | پروفایل مشتری، درخواست توکن از مربی |
| `personal` | `POST /api/auth/register-personal/` | فقط برنامه‌های خودش (نیازمند `training_place`) |

مشترک بین همه: گرفتن/ویرایش برنامه، خرید توکن، پروفایل و تغییر رمز.
جدول کاربران یکی است (جنگو فقط یک `AUTH_USER_MODEL` می‌پذیرد) اما مرز دسترسی‌ها در `app/permissions.py` سخت‌گیرانه اعمال و تست شده است.

## مربی و برنامه‌های مشتریان

مربی می‌تواند برای هر مشتری برنامه بسازد و **همان برنامه را هم ویرایش کند** (هزینه از حساب خودش کسر می‌شود).
`GET /api/programs/history/?client_id=<id>` هر دو نوع برنامه‌ی آن مشتری را برمی‌گرداند:

- برنامه‌ای که مربی برای او ساخته (`ClientProgram.user` = مربی، `name` = نام مشتری)
- برنامه‌ای که خود ورزشکار با اکانتش ساخته (`ClientProgram.user` = اکانت ورزشکار)

چون `ClientProgram` رابطه‌ی مستقیمی با `GymClient` ندارد، اتصال حالت اول از روی **نام مشتری** برقرار می‌شود؛
پس هنگام ساخت کد دسترسی نام مشتری را ثبت کنید و در ساخت برنامه هم همان نام را بفرستید
(صفحه `try/06-coach-clients.html` این کار را با انتخاب مشتری از فهرست انجام می‌دهد).

## کار دوره‌ای (Cron)

```bash
python manage.py reclaim_expired_tokens           # بازگشت توکن‌های رزروشده منقضی
python manage.py reclaim_expired_tokens --dry-run # فقط گزارش، بدون تغییر
```

مهلت از پنل ادمین تنظیم می‌شود: **تنظیمات سامانه → مهلت توکن رزروشده (روز)** (پیش‌فرض ۳۰، مقدار ۰ = غیرفعال).
پیشنهاد: روزی یک‌بار با cron یا Task Scheduler اجرا شود. اکشن دستی هم در ادمین روی «مشتریان باشگاه» وجود دارد.

## پرداخت

`PurchaseTokenView` به `payment_gateway.py` وصل است: با تنظیم یک **درگاه فعال** در پنل ادمین (زرین‌پال و آیدی‌پی کامل، نکست‌پی تا حد زیادی)، پاسخ ثبت سفارش `payment_url` واقعی برمی‌گرداند و `PaymentCallbackView` پرداخت را **مستقیماً با خود درگاه verify** می‌کند — کال‌بک جعلی توکن نمی‌دهد. بدون درگاه فعال، سفارش pending می‌ماند و شارژ با اکشن ادمین («پرداخت‌شده + شارژ توکن») انجام می‌شود.

### تست پرداخت بدون پول واقعی (درگاه mock)

برای اینکه کل مسیر پرداخت روی لوکال قابل تست باشد، یک **درگاه تستی داخلی** وجود دارد که هیچ تماس شبکه‌ای ندارد:

```bash
python manage.py setup_mock_gateway          # فعال‌سازی
python manage.py setup_mock_gateway --off    # غیرفعال‌سازی
```

یا از پنل ادمین → «تنظیمات درگاه پرداخت» → نوع درگاه = **درگاه تستی**، Callback URL = `http://localhost:8000/api/payment-callback/`، تیک «فعال». (`merchant_id` برای این درگاه لازم نیست.)

بعد از آن `POST /api/purchase-token/` یک `payment_url` به صفحه شبیه‌ساز `/api/mock-payment/` می‌دهد؛ آن صفحه مبلغ سفارش را نشان می‌دهد و با دکمه‌های «پرداخت موفق / انصراف»، کاربر را با `Status=OK` یا `Status=NOK` به همان کال‌بک واقعی برمی‌گرداند. یعنی مسیر verify، idempotency و شارژ توکن دقیقاً مثل درگاه واقعی طی می‌شود.

**واقعی‌کردن:** فقط کافی است در پنل ادمین درگاه واقعی را فعال کنید — هیچ تغییری در کد لازم نیست.

**ایمنی production:** درگاه تستی با `settings.ALLOW_MOCK_PAYMENT_GATEWAY` کنترل می‌شود که پیش‌فرضش برابر `DEBUG` است. اگر `DJANGO_DEBUG=False` باشد، درگاه تستی خاموش است (تراکنش با خطای صریح رد می‌شود و صفحه شبیه‌ساز 404 می‌دهد) مگر اینکه عمداً `DJANGO_ALLOW_MOCK_GATEWAY=1` ست شود — تا سروری که اشتباهاً روی درگاه تستی مانده، توکن رایگان تحویل ندهد.

### پرداخت کارت‌به‌کارت

روش دوم پرداخت، برای وقتی که درگاه آنلاین در دسترس نیست. کل مسیر:

1. مدیر در ادمین → **حساب‌های کارت‌به‌کارت** یک کارت می‌سازد و `فعال` می‌زند (فقط یکی می‌تواند فعال باشد).
2. کلاینت `GET /api/payment-card/` می‌زند؛ اگر `enabled=false` بود، نباید گزینه کارت‌به‌کارت را نشان بدهد.
3. `POST /api/purchase-token/` با `payment_method=card` سفارش را با وضعیت `awaiting_receipt` می‌سازد و شماره کارت را برمی‌گرداند. **هیچ توکنی داده نمی‌شود.**
4. کاربر واریز می‌کند و رسید را با `POST /api/purchase-token/<id>/receipt/` (multipart) بالا می‌دهد → وضعیت `under_review`.
5. مدیر در ادمین → **خریدهای توکن**، سفارش را انتخاب و اکشن **«✅ تایید رسید کارت‌به‌کارت و آزادسازی توکن»** را اجرا می‌کند. تنها همین‌جا توکن آزاد می‌شود.

نکات امنیتی که در کد تضمین شده‌اند:

- تغییر دستی وضعیت به `paid` در فرم ادمین **توکن شارژ نمی‌کند**؛ فقط اکشن تایید این کار را می‌کند و idempotent است (اجرای دوباره، دوبار شارژ نمی‌کند).
- سفارش کارت‌به‌کارت از مسیر کال‌بک درگاه قابل تایید نیست.
- سفارشی بدون رسید تایید نمی‌شود.
- رسید هر کاربر فقط توسط خودش یا کاربر `staff` قابل دیدن است.

### محل ذخیره رسیدها (حساس)

تصویر رسید بانکی داده‌ی حساس است، پس **بیرون از `MEDIA_ROOT`** و در `PRIVATE_MEDIA_ROOT` ذخیره می‌شود تا وب‌سرور مستقیماً سروش نکند. دسترسی فقط از این مسیر است:

```
GET /api/purchase-token/<id>/receipt/file/     # نیازمند احراز هویت؛ صاحب سفارش یا staff
```

اگر `PRIVATE_MEDIA_ROOT` را جابه‌جا کردید، مطمئن شوید داخل `MEDIA_ROOT` یا مسیر `location` نگینکس نیفتد. `python manage.py check --deploy` این را بررسی می‌کند (`gym.E002`).

## حسابداری (فقط خواندنی)

سه بخش در ادمین که **عمداً غیرقابل افزودن/ویرایش/حذف** هستند تا اعداد مالی قابل استناد بمانند:

| بخش | چه چیزی نشان می‌دهد |
|---|---|
| **دفتر حساب** | هر رویداد مالی/توکنی به‌صورت append-only: خرید، شارژ، مصرف، بازگشت، کمیسیون، هزینه هوش مصنوعی |
| **حسابداری — صورت‌حساب کاربران** | برای هر کاربر: مبلغ پرداختی، توکن خریداری‌شده، توکن مصرف‌شده، تعداد برنامه، هزینه واقعی AI، سود ناخالص |
| **استفاده‌های کد تخفیف** | سهم/کمیسیون سازنده هر کد از هر خرید |

`LedgerEntry.save()` روی رکورد موجود و `delete()` عمداً `ValueError` می‌دهند — حتی از shell هم نمی‌شود سطر را دست‌کاری کرد. تغییر دستی موجودی از فرم کاربر در ادمین هم یک سطر با ردپای اپراتور در دفتر ثبت می‌کند.

## ارائه‌دهنده‌های هوش مصنوعی (زنجیره‌ی اولویت)

در ادمین → **ارائه‌دهنده‌های هوش مصنوعی** می‌توانید چند ارائه‌دهنده تعریف کنید و برایشان **اولویت** بگذارید. هنگام ساخت یا ویرایش برنامه، زنجیره به ترتیب اولویت پیمایش می‌شود و **اولین ارائه‌دهنده‌ای که پاسخ بدهد** استفاده می‌شود.

اگر ارائه‌دهنده‌ی اول در دسترس نباشد — سرور محلی خاموش، اینترنت قطع، اعتبار تمام‌شده، مهلت تمام‌شده، خطای ۵xx، یا حتی پاسخ خالی — سامانه **خودکار سراغ بعدی می‌رود** و کاربر هیچ خطایی نمی‌بیند. فقط وقتی خطا به کاربر می‌رسد که **همه‌ی** ارائه‌دهنده‌های فعال شکست بخورند (و در آن حالت هم توکن کاربر برگردانده می‌شود).

### دو نوع ارائه‌دهنده

| | سرویس ابری | مدل محلی / سرور خودم |
|---|---|---|
| نوع | «سرویس ابری (با کلید API)» | «مدل محلی / سرور خودم (فقط آدرس)» |
| آدرس | `https://api.openai.com/v1` (کامل) | `http://192.168.1.50:11434` ← **فقط همین** |
| کلید API | الزامی | **لازم نیست** |
| نام مدل | الزامی (`gpt-4o-mini`) | **لازم نیست** — خودکار خوانده می‌شود |
| تعرفه | از صورتحساب سرویس‌دهنده | معمولاً صفر (رایگان) |
| مهلت پاسخ | پیش‌فرض ۱۸۰ ثانیه | سخت‌افزار ضعیف = عدد بزرگ‌تر (مثلاً ۳۰۰) |

هر دو نوع از پروتکل سازگار با OpenAI استفاده می‌کنند. اولاما (Ollama)، vLLM و LM Studio همین درگاه را ارائه می‌دهند، پس کد یکسانی هر دو را صدا می‌زند.

### برای سرور خودتان فقط لینک کافی است

دو چیزی که معمولاً باید دستی وارد می‌شد، خودکار حل می‌شوند:

* **مسیر `/v1`** — اگر فقط `http://192.168.1.50:11434` بدهید، خودش `‎/v1` را اضافه می‌کند. اگر خودتان مسیر داده باشید (مثلاً یک reverse proxy روی `https://ai.mydomain.com/api/v1`)، دست نمی‌خورد.
* **نام مدل** — خالی بگذارید. سامانه فهرست مدل‌های سرور را از `‎/models` می‌خواند و اولی را برمی‌دارد. نتیجه تا ۶ ساعت کش می‌شود تا هر تولید برنامه یک رفت‌وبرگشت اضافه نزند. اگر آدرس یا نوع ارائه‌دهنده را عوض کنید، کش خودکار باطل می‌شود.

اگر چند مدل روی سرور دارید و یکی خاص را می‌خواهید، اکشن **«🔍 خواندن فهرست مدل‌های سرور»** را بزنید تا نام دقیق همه را ببینید، بعد آن را در «نام مدل» بنویسید. نام صریح همیشه بر کشف خودکار اولویت دارد.

### راه‌اندازی مدل محلی با اولاما

روی سیستم یا سروری که مدل را اجرا می‌کند:

```bash
ollama serve                      # پیش‌فرض روی پورت 11434
ollama pull llama3.2              # دانلود مدل
```

اگر می‌خواهید از بیرون در دسترس باشد، اولاما باید روی همه‌ی اینترفیس‌ها گوش بدهد:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

سپس در ادمین یک ارائه‌دهنده بسازید — فقط دو فیلد:

* نوع: **مدل محلی / سرور خودم**
* آدرس: `http://SERVER_IP:11434`
* اولویت: ۱ (تا اول از همه امتحان شود)

کلید API و نام مدل را خالی بگذارید. همین.

> **امنیت:** اگر سرور اولاما را روی اینترنت باز می‌کنید، جلوی آن یک reverse proxy با احراز هویت بگذارید یا با فایروال فقط IP سرور جنگو را مجاز کنید. اولاما خودش احراز هویت ندارد. اگر پشت پراکسی با کلید گذاشتید، همان کلید را در فیلد «کلید API» وارد کنید — پذیرفته می‌شود.

### مثال چیدمان

| اولویت | نام | نوع | توضیح |
|---|---|---|---|
| ۱ | اولامای سرور خودم | محلی | رایگان، اول امتحان می‌شود |
| ۲ | متیس | ابری | اگر سرور خودم خواب بود |
| ۳ | اوپن‌ای‌آی | ابری | آخرین پشتیبان |

با این چیدمان، هزینه‌ی معمول شما صفر است و فقط وقتی سرور محلی مشکل دارد، پول خرج می‌شود.

### تست اتصال پیش از استقرار

در فهرست ارائه‌دهنده‌ها، مورد یا موارد دلخواه را انتخاب کنید و اکشن **«🔌 تست اتصال ارائه‌دهنده‌های انتخاب‌شده»** را اجرا کنید. یک درخواست کوچک واقعی فرستاده می‌شود تا معلوم شود آدرس، کلید و نام مدل درست‌اند — به‌جای اینکه اولین کاربر متوجه اشکال شود.

ستون **«وضعیت آخرین اتصال»** در همان فهرست، نتیجه‌ی آخرین استفاده‌ی واقعی هر ارائه‌دهنده را نشان می‌دهد (سبز = موفق، قرمز = پیام خطا).

### سازگاری خودکار با خانواده‌های مختلف مدل

هر خانواده‌ی مدل پارامترهای کمی متفاوتی می‌پذیرد. مدل‌های استدلالی اوپن‌ای‌آی (مثل `gpt-5` و سری `o`) به‌جای `max_tokens` فقط `max_completion_tokens` را قبول می‌کنند و `temperature` سفارشی را رد می‌کنند:

```
Error code: 400 - Unsupported parameter: 'max_tokens' is not supported with this model.
Use 'max_completion_tokens' instead.
```

سامانه این را خودش تشخیص می‌دهد (از فیلد `param` خودِ پاسخ خطا، نه از روی متن پیام) و درخواست را با پارامتر درست دوباره می‌فرستد. **نتیجه روی همان ارائه‌دهنده ذخیره می‌شود** و در ادمین زیر «سلامت اتصال» دیده می‌شود، پس این کشف فقط یک بار هزینه می‌دهد؛ تولیدهای بعدی مستقیم می‌روند. با تغییر آدرس یا نام مدل، کشف قبلی پاک می‌شود چون مدل جدید ممکن است خانواده‌ی دیگری باشد.

اکشن «🔌 تست اتصال» هم از همین مسیر می‌گذرد، یعنی اگر آن را قبل از استقرار بزنید، اولین کاربر واقعی حتی همان یک بار را هم نمی‌پردازد.

### مقاومت در برابر قطعی گذرا

- **تایم‌اوت یا خطای ۵xx/۴۲۹** یک بار تکرار می‌شود و بعد سراغ ارائه‌دهنده‌ی بعدی می‌رویم. وقتی فقط یک ارائه‌دهنده تنظیم شده باشد، زنجیره‌ای برای عقب‌نشینی وجود ندارد و بدون این تکرار، یک قطعی لحظه‌ای کل تولید برنامه را می‌سوزاند.
- **مهلت اتصال** جدا از مهلت پاسخ است (۱۰ ثانیه). سروری که اصلاً بالا نیست در چند ثانیه رد می‌شود، نه بعد از کل مهلت پاسخ.
- **مدل استدلالی که همه‌ی بودجه را صرف «فکر کردن» می‌کند** و متنی برنمی‌گرداند، یک بار با بودجه‌ی بزرگ‌تر دوباره پرسیده می‌شود. قبلاً این حالت «خروجی خالی» شمرده می‌شد و کل زنجیره می‌سوخت، در حالی که مدل سالم بود.

## هزینه توکن هوش مصنوعی

برای هر ارائه‌دهنده دو عدد وارد کنید: «قیمت هر یک میلیون توکن ورودی» و «خروجی» (تومان). از آن به بعد هر برنامه، مصرف واقعی مدل و هزینه‌اش را ذخیره می‌کند و در فهرست **برنامه‌های مشتری** ستون «هزینه هوش مصنوعی» دیده می‌شود. اگر تعرفه صفر بماند، هزینه محاسبه نمی‌شود و به‌جای عدد ساختگی «— تعرفه ثبت نشده» نمایش داده می‌شود.

هزینه همیشه با تعرفه‌ی **همان ارائه‌دهنده‌ای** حساب می‌شود که واقعاً پاسخ داده. اگر زنجیره به ارائه‌دهنده‌ی دوم رفته باشد، تعرفه‌ی دومی اعمال می‌شود — نه اولی. پس اگر مدل محلی رایگانتان پاسخ داده، هزینه‌ی آن برنامه صفر ثبت می‌شود.

## تنظیمات production (env-محور)

تنظیمات حساس از متغیر محیطی خوانده می‌شوند:

| متغیر | توضیح |
|---|---|
| `DJANGO_SECRET_KEY` | کلید مخفی (پیش‌فرض فقط برای توسعه) |
| `DJANGO_DEBUG` | `False` در production |
| `DJANGO_ALLOWED_HOSTS` | دامنه‌ها با کاما |
| `DJANGO_CORS_ALLOWED_ORIGINS` | originهای مجاز فرانت (فقط وقتی DEBUG=False) |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | originهای معتبر CSRF |
| `DJANGO_ALLOW_MOCK_GATEWAY` | `1` برای اجازه درگاه پرداخت تستی وقتی `DEBUG=False` (پیش‌فرض: خاموش) |
| `GYM_PDF_FONT_PATH` | مسیر فونت فارسی (TTF) برای PDF روی سروری که WeasyPrint ندارد |
| `DJANGO_PRIVATE_MEDIA_ROOT` | محل ذخیره فایل‌های حساس (رسید پرداخت). پیش‌فرض: `private_media/` کنار پروژه. **نباید داخل `MEDIA_ROOT` باشد.** |
| `DJANGO_SECURE_SSL_REDIRECT` | اجبار HTTPS. **پیش‌فرض روشن** وقتی `DEBUG=False` |
| `DJANGO_BEHIND_TLS_PROXY` | اگر TLS روی nginx/کلادفلر terminate می‌شود. **پیش‌فرض روشن** — nginx باید `proxy_set_header X-Forwarded-Proto $scheme` بدهد |
| `DJANGO_HSTS_SECONDS` | مدت HSTS. پیش‌فرض `31536000` (یک سال) |
| `DJANGO_HSTS_SUBDOMAINS` | شمول زیردامنه‌ها در HSTS. پیش‌فرض روشن |
| `DJANGO_HSTS_PRELOAD` | ثبت در فهرست preload مرورگرها. **پیش‌فرض خاموش** — عمداً، چون برگشت از آن بسیار سخت است |

CSRF فعال است، CORS فقط در DEBUG باز است و در حالت production کوکی‌های امن، `X-Frame-Options: DENY`، `Referrer-Policy: same-origin`، اجبار HTTPS و HSTS یک‌ساله ست می‌شوند.

> **هشدار حلقه ریدایرکت:** اگر پشت nginx هستید و `proxy_set_header X-Forwarded-Proto $scheme` را نگذاشته باشید، جنگو هر درخواست را HTTP می‌بیند و بی‌نهایت به HTTPS ریدایرکت می‌کند. یا آن هدر را تنظیم کنید، یا `DJANGO_BEHIND_TLS_PROXY=0` بگذارید.

### چک‌لیست قبل از استقرار

```bash
python manage.py check --deploy
```

بررسی‌های اختصاصی این پروژه (در `app/checks.py`) که آنجا اجرا می‌شوند:

| کد | چه چیزی را می‌گیرد |
|---|---|
| `gym.W001` | WeasyPrint نصب نیست **و** هیچ فونت فارسی پیدا نشد → PDF ناخوانا تولید می‌شود |
| `gym.E001` | `PRIVATE_MEDIA_ROOT` تنظیم نشده |
| `gym.E002` | `PRIVATE_MEDIA_ROOT` داخل `MEDIA_ROOT` عمومی است → رسیدها لو می‌روند |
| `gym.W002` | درگاه پرداخت تستی روی production روشن مانده → توکن رایگان |

**فونت PDF روی سرور لینوکسی:**

```bash
apt-get install fonts-vazirmatn
export GYM_PDF_FONT_PATH=/usr/share/fonts/truetype/vazirmatn/Vazirmatn-Regular.ttf
```

اگر WeasyPrint نصب باشد این لازم نیست (فونت را از fontconfig سیستم می‌گیرد)، اما داشتنش ضرری ندارد چون در صورت خطای WeasyPrint، مسیر ReportLab فعال می‌شود.
