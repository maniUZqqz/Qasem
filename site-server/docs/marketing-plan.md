# برنامهٔ بازاریابی، راهنمای آزمونِ بخش‌ها و «گزارشِ ایراد» (`apps/mktplan`)

این سه کار یک اپِ جنگو هستند، چون یک هدف دارند: **یک فروشگاهِ واقعی را با همهٔ بخش‌های NM بازاریابی کنیم و هر ایرادی که در آزمون دیده شد به رفعِ ایراد برسد.**
هیچ‌چیزِ مخصوصِ یک فروشگاه در کد نیست؛ چغر (فروشگاه ۳۴) فقط اولین استفادهٔ واقعی است.

## ۱) برنامهٔ بازاریابی

صفحه: «محتوا ⇐ برنامهٔ بازاریابی» (`/panel/stores/<id>/marketing-plan`).

برنامه دو‌هفته‌ای است (۴۵ کار، ۱۴ روز؛ شروع پیش‌فرض فردا). هر کار: روز، نوع، بخشِ پنل که آن را می‌سازد، عنوان، توضیح، پیش‌نویسِ متنی، پیوند به چیزهای ساخته‌شده و وضعیتِ زنده.

| گروه | نوع‌ها |
|---|---|
| راه‌اندازی | بانکِ ایده، ترند، صندوقِ پیام |
| محتوا | پروفایل (بایو/هایلایت)، پست، کاروسل، استوری، ریلز |
| رسانه (GPU) | تصویرِ FLUX، کاورِ تامنیل، شخصیتِ برند، موشن، گوینده (با لایهٔ تلفظ)، موسیقی، ویدیو از ارائه، ویدیوی سه‌بعدی |
| طراحی | کاتالوگ، ارائه، صفحهٔ فرود (پیش‌نویسِ سایت‌ساز) |
| پیام‌رسانی | ایمیل، پیامک (ارسالِ گروهیِ پیش‌نویس)، دایرکتِ مشتری‌یاب |
| جذبِ مشتری | مأموریتِ مشتری‌یاب، بازبینیِ لیدها |
| تصمیمِ مالک | نظرِ واقعیِ مشتری، بازبینیِ هفتگی |

### «اول می‌پذیرد، بعد می‌سازد»

هر تولیدکننده (`producers.py`) اول می‌بیند فروشگاه از دورهای قبل چیزی دارد که به این کار بخورد (کارِ کمپین با همان قالب، رندرِ موشنِ منتظر، تامنیلِ منتظرِ پس‌زمینه، سندِ طراحی، مأموریتِ مشتری‌یاب، پیش‌نویسِ مشتری‌یاب، صدای آماده…) و همان را وصل می‌کند؛ موعدِ کارِ کمپینِ کهنه تازه می‌شود (فقط همان یک خطِ «موعدِ پیشنهادیِ انتشار»). فقط اگر چیزی نبود می‌سازد. اجرای دوباره هرگز چیزِ تکراری نمی‌سازد.

### وضعیت از روی چیزِ ساخته‌شده خوانده می‌شود

هر کار فقط یک «اشاره» (`refs`) دارد؛ وضعیتش را `runner.derive` هر بار از روی خودِ ردیفِ مقصد می‌خواند (همان اصلِ تختهٔ کمپین). تنها چیزی که در خودِ کار ذخیره می‌شود «تصمیمِ مالک» است (تأیید / منتشر شد / رد).

وضعیت‌ها: `PLANNED`، `DRAFTED` (پیش‌نویس آماده)، `WAITING_NODE` (منتظرِ سرورِ پردازش)، `RUNNING`، `READY` (آماده برای تأیید)، `NEEDS_YOU` (فقط مالک می‌تواند)، `FAILED`.

### سرورِ پردازش و هوش مصنوعی

* **هیچ کارِ GPU خطا نیست وقتی گره خاموش است.** رندرِ موشن، گوینده، موسیقی، تامنیلِ FLUX، تصویرِ شخصیت و ویدیو از ارائه با همان سرویسِ بخشِ خودشان در *صفِ ماندگار* می‌روند (همان‌هایی که در «صفِ پردازش» دیده می‌شوند) و با روشن‌شدنِ گره خودشان اجرا می‌شوند.
* **تیکِ پس‌زمینه** (`tasks.tick`، هر ۱۰ دقیقه، Celery beat): وضعیت‌ها را تازه می‌کند (`motion.services.refresh`, `thumbs.services.refresh`, `audio studio.sync` … همان توابعی که صفحهٔ هر بخش هنگامِ باز شدن صدا می‌زند)، کارهای `WAITING_NODE`/`PLANNED`/`FAILED` را وقتی گره روشن شد دوباره می‌سازد (تا ۶ بار) و پولیشِ هوش مصنوعی را پیش می‌برد.
* **ترتیبِ هوش مصنوعی همان ترتیبِ پروژه است**: لوکال (Ollama روی گره) اول، متیس دوم (`ideabank.ai`، مسیریابِ `services/ai`). پیش‌نویس‌ها اول قاعده‌محورند (فقط از واقعیت‌های فروشگاه + جای‌گیرِ «[ ]»)؛ وقتی هوش مصنوعی در دسترس بود با لحنِ شخصیتِ برند بازنویسی می‌شوند (`ai.polish`). بازنویسی‌ای که یک جای‌گیر را بردارد یا عدد/قیمت/ادعای تازه بیاورد پذیرفته نمی‌شود. متیسِ بی‌اعتبار (۴۰۲) فقط پیامِ روشن می‌دهد و پیش‌نویسِ قاعده‌محور می‌ماند.
* **آزمونِ خودکارِ گره** (`compute/selftests/mktplan.py`، مجازی و بی‌کارِ تازه): بعد از روشن‌شدنِ سرور می‌سنجد هیچ کارِ GPUِ برنامه تا ۴۵ دقیقه «منتظر» یا «ناموفق» نمانده باشد.

### چیزی که هرگز نمی‌شود

* چیزی منتشر یا فرستاده نمی‌شود. پیامک فقط یک «ارسالِ گروهی»ِ `DRAFT` است که تا «پیش‌نمایش ⇐ ارسال برای تأیید ⇐ تأییدِ مالک» نمی‌رود؛ ایمیل فقط متن است؛ سایت منتشر نمی‌شود.
* هیچ قیمت، درصد، آمار یا نظرِ مشتریِ ساخته‌شده‌ای نیست. هرجا داده‌ای فقط مالک دارد «[پیشنهادِ واقعیِ شما]» می‌ماند و نظرِ مشتری همیشه `NEEDS_YOU` است. نگهبانِ `drafts.check` عدد/قیمتِ بی‌منبع و واژه‌های «نگو»ی شخصیتِ برند را زیرِ هر پیش‌نویس هشدار می‌دهد.

## ۲) اجرا برای یک فروشگاه

```
cd backend
python manage.py marketing_plan_run --store 34            # بساز + اجرا (تکرارپذیر)
python manage.py marketing_plan_run --name چغر --restart  # شروع را به فردا ببر
python manage.py marketing_plan_run --store 34 --report   # فقط گزارش
python manage.py marketing_plan_run --store 34 --tick     # یک تیکِ پس‌زمینه
```

یا از پنل: «ساخت و اجرا». پس از آن همه‌چیز خودکار است (تیکِ ده‌دقیقه‌ای + آزمونِ گره).

## ۳) راهنمای آزمونِ بخش‌ها

صفحه: «محتوا ⇐ راهنمای آزمونِ بخش‌ها». منبعِ حقیقت `guide.py` است؛ سندِ `docs/chagher/test-guide-fa.md` از همان ساخته می‌شود:

```
python manage.py mktplan_guide_md --out ../docs/chagher/test-guide-fa.md --store 34
```

آزمونِ `tests_guide` تضمین می‌کند **هر صفحهٔ دفترِ پنل** (`apps/panel/registry.py`) در یکی از بخش‌های راهنما پوشش دارد و سندِ موجود با داده یکی است؛ پس صفحه‌ای که بعداً اضافه شود بی‌راهنما نمی‌ماند (آزمون می‌شکند تا کسی راهنما را به‌روز کند).

## ۴) گزارشِ ایراد

دکمهٔ «ایراد؟» کنارِ قرصِ نسخه در هر صفحهٔ پنل (و دکمه‌های «گزارشِ ایراد» در راهنما و برنامه). پنجره: بخش (پیش‌انتخاب از روی صفحه)، یادداشت، عکس (فایل / Ctrl+V / «گرفتنِ عکسِ صفحه»). همراهش خودکار: نشانیِ صفحه، نسخه، اندازهٔ صفحه، مرورگر، آخرین خطاهای API و جاوااسکریپتِ همان صفحه.

ذخیره: جدولِ `mktplan_bugreport` + عکس در `MEDIA_ROOT/bug-reports/`. خواندن برای رفعِ ایراد:

```
python manage.py bug_reports                 # جدید و دیده‌نشده
python manage.py bug_reports --all --json    # ماشینی (با نشانیِ عکس و زمینه)
python manage.py bug_reports --mark 12 fixed
```

API: `POST /api/v1/bug-reports/` (چندبخشی)، `GET /api/v1/bug-reports/` (کارکنان همه، دیگران فقط مالِ خود)، `PATCH /api/v1/bug-reports/<id>/` (کارکنان).
