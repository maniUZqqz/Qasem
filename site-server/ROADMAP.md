## ۱. چشم‌انداز محصول

UpMarket یک **«کارمند فروش و مارکتینگ هوش مصنوعی» برای فروشگاه‌های آنلاین** است — نه صرفاً یک ابزار تولید محتوا.

صاحب فروشگاه باید بتواند:

1. فروشگاه بسازد و اطلاعات برند/کسب‌وکارش را وارد کند.
2. محصولات را با عکس، قیمت، موجودی و مشخصات اضافه کند.
3. هوش مصنوعی محصولات را **تحلیل** کند (تحلیل بصری + استراتژی) و با رقبا مقایسه کند.
4. **چت‌بات فروش** کامل داشته باشد که بدون نیاز به انسان، مثل آنلاین‌شاپ‌ها پاسخ دهد، پیشنهاد بدهد، اعتراض مشتری را مدیریت کند و سفارش ثبت کند.
5. **پوستر تبلیغاتی** + کپشن آن تولید کند.
6. **عکس محصول را ادیت/حرفه‌ای** کند (آماده اینستاگرام) + کپشن آن.
7. **سناریوی ویدیوی تبلیغاتی** بنویسد + کپشن.
8. ویدیو را **قطعه‌قطعه ۵ ثانیه‌ای** تولید کند (محدودیت مدل ویدیو) و به هم بچسباند؛ **فریم آخر هر قطعه، ورودی قطعه بعدی** می‌شود تا ویدیو پیوسته باشد.
9. روی ویدیو **صداگذاری (TTS)** هماهنگ با سناریو انجام دهد.
10. محتوای تأییدشده را از طریق **n8n** در شبکه‌های اجتماعی منتشر کند.
11. در آینده: آنالیتیکس و یادگیری از نتایج برای بهبود تصمیم‌های بعدی.

فلسفه اصلی:

```
STORE DATA → PRODUCT KNOWLEDGE → MARKET INTELLIGENCE → AI STRATEGY
→ CONTENT → CUSTOMER CONVERSATION → SALE → PUBLISHING → ANALYTICS → LEARNING
```

### ۲.۴. راه‌اندازی سرور Ollama (روی سرور)

قبل از `ollama serve` متغیرهای محیطی را تنظیم کن (PowerShell):

```powershell
# Flash Attention و پردازش موازی
$env:OLLAMA_FLASH_ATTENTION = 1
$env:OLLAMA_NUM_PARALLEL = 2

# طول کانتکست — بهترین تعادل سرعت/کانتکست برای این سیستم: 8192
$env:OLLAMA_CONTEXT_LENGTH = 8192
# یا به صورت دائمی:
setx OLLAMA_NUM_CTX 131072

ollama serve
```

نمایش کانتکست و مشخصات مدل:

```powershell
ollama show qwen3-coder:30b
```

## ۴. وضعیت فعلی ریپو

**(به‌روزرسانی ۲۰۲۶/۰۸/۲۷ — سه بخش قدیمی در پروژه واحد `backend/` ادغام شدند)**

- `backend/` — **پروژه واحد Django** (ادغام API + json + Main):
  - `apps/accounts` (JWT)، `apps/stores`، `apps/products`، `apps/jobs`، `apps/ai` (هوش محصول + تحلیل بازار + embeddings)، `apps/customers` (ایجنت فروش + سفارش + رسید پرداخت + تیکت + اعلان)، `apps/content` (کپشن/تصویر/سناریو/ویدیو/صدای دوزبانه)، `apps/campaigns` (کمپین + انتشار n8n)، `apps/analytics` (+ داشبورد فروش)
  - `services/` — ai (Ollama + روتر + embeddings + پرامپت‌های نسخه‌دار)، comfyui (کلاینت + ۳ ورک‌فلوی نسخه‌دار)، video (FFmpeg)، audio (edge-tts/gTTS دوزبانه)، research (دیجی‌کالا/ترب/SearXNG/Brave)، publishing (n8n)
  - **۱۱۸ تست — همه سبز ✅** (AI با mock، FFmpeg و ریسرچ واقعی)
  - **اصلاحات پایداری (۲۰۲۶/۰۸/۲۷):** گراف FLUX txt2img اصلاح شد (cfg=1.0 + نود FluxGuidance — قبلاً cfg=7 خروجی را می‌سوزاند)؛ بن‌بست انتشار n8n رفع شد (ریست PENDINGهای رهاشده + جلوگیری از پست تکراری با skip پلتفرم‌های SENT)؛ گارد دوبار-کلیک برای تولید ویدیو/صدا (409 + خود-ترمیمی Job مرده)؛ تولید ویدیو در حالت synchronous بلاک می‌شود (نیازمند صف)؛ `start.bat` دو worker جدا (ai/gpu) اجرا می‌کند تا ویدیو بقیه Jobها را بلاک نکند؛ فرانت: سقف خطای polling + رفع نشتی interval + دریافت همه صفحات pagination + فونت وزیرمتن باندل‌شده
  - **اصلاحات بازخورد تست واقعی — beter.md (۲۰۲۶/۰۸/۲۹، هر ۱۱ مورد):** تاریخچه چت در UI؛ ترمیم چندمرحله‌ای JSON مدل + یک تلاش خوداصلاحی مدل (`generate_json`) و رفع قطع‌شدن خروجی (کانتکست ۲۰۴۸→۸۱۹۲ + KV q8_0 در start.bat، تایم‌اوت Ollama ۱۸۰→۶۰۰ برای لود سرد مدل ۳۲B)؛ ادامه خودکار polling بعد از رفرش (`useJobRunner.resume` + فیلترهای `/jobs/`) و کامپوننت `JobProgress` با نوار پیشرفت/کرونومتر؛ پوستر حالا img2img از عکس واقعی محصول + **درج متن فارسی با کد** (Pillow + وزیرمتن باندل‌شده + RTL، `services/imaging/text_overlay.py`) و بن سخت text در negative؛ تحلیل بازار v3 با `competitors`/`comparison` ساختاریافته + کارت رقبا در UI؛ کپشن به محتوای مشخص وصل شد (`Caption.about_image/about_video` + انتخاب‌گر در UI، پرامپت v3)؛ هماهنگ‌کننده GPU (`services/gpu.py`: آنلود Ollama قبل از ComfyUI و برعکس، `GPU_AUTO_UNLOAD`)؛ `GET video-script` حالا 200+null؛ پشتیبانی Redis پرتابل در start.bat + پیام‌های 503 راهنما؛ فلگ‌های v7 React Router. **۱۳۲ تست سبز.**
- `frontend/` — **داشبورد React** (Vite + TypeScript + Tailwind v4، فارسی RTL): احراز هویت، فروشگاه/محصول، پنل‌های هوش محصول، تحلیل بازار (+نتایج وب)، استودیوی تصویر، کپشن‌ها، استودیوی ویدیو (+صداگذاری)، چت فروش، کمپین‌ها و انتشار، صفحه آمار
- `start.bat` — **لانچر یک‌کلیکی** با pre-flight کامل: چک پایتون/نود/ffmpeg، ساخت خودکار `.env`، نصب خودکار پکیج‌ها، migrate، ساخت کاربر ادمین (admin/admin1234)، اجرای همه سرویس‌ها، و health-check با گزارش [OK]/[WARN]/[FAIL]
- `test.md` — چک‌لیست کامل تست شبانه + جدول خطایابی
- `docs/` — مستندات معماری فاز ۰
- آرشیوهای قدیمی (`_archive_old_code/`، `_archive_old_docs/`) در ۲۰۲۶/۰۸/۲۷ **حذف شدند** — هرچه لازم بود قبلاً منتقل شده

### ۸.۴ — AI Gateway

در فاز فعلی پیشنهاد می‌شود **Text AI + Analysis AI + بخشی از Vision به API منتقل شوند.**

این مستقیماً [نقص ۴](#نقص-۴--مدل-ظرفیت-زمان-llm-را-صفر-گرفته) را حل می‌کند: اگر LLM روی GPU نباشد، GPU فقط برای FLUX/Wan می‌ماند و مدل ظرفیت واقعی می‌شود.

```text
    └── Future Local Models
```

### ۸.۵ — Hardware-Aware Scheduling

نباید بر اساس نام مدل یا حدس، ظرفیت را حساب کرد.

#### Hardware Profiler

سیستم هنگام Startup سخت‌افزار را بخواند:

```text
GPU
 ├── VRAM
 ├── Available VRAM
 ├── CUDA Capability
 ├── Temperature
 ├── Utilization
 └── Concurrent Capacity
```

#### تخمین هزینه‌ی هر Job

```text
Estimated Cost =
    Model Load
  + Model Swap
  + Inference
  + Rendering
  + Post Processing
  + Encoding
  + Validation
  + Retry Probability
```

#### فرمول ظرفیت واقعی

```text
Effective Capacity =
    GPU Available Time
    ─────────────────────────────────────────
    Generation + Model Load + Model Swap
    + Encoding + QC + Retry
```

و بعد **با ضریب اطمینان**. نباید از ۱۰۰٪ ظرفیت GPU در Business Model استفاده کرد. Capacity Reserve لازم است برای: Failures، Maintenance، Traffic Spikes، Retry، Queue، Monitoring.

#### Smart Scheduler

هر کار روی سخت‌افزار مناسبش:

```text
Cut              → CPU
Audio processing → CPU
Color            → CPU/GPU
AI Enhancement   → GPU
Video Generation → GPU
Encoding         → CPU/GPU
```

و اگر GPU درگیر Generation است، کارهای غیرضروری نباید آن را اشغال کنند.

### ۸.۶ — Async و Real-Time

#### هر عملیات سنگین = یک Job

هیچ عملیات سنگینی نباید داخل Request وب انجام شود.

به‌جای:

```text

```

باید:

```text
POST /jobs → job_id → GET /jobs/{id}
```

```text
QUEUED → PROCESSING → PREVIEW → WAITING_APPROVAL
→ APPROVED → RENDERING → QC → COMPLETED
```

### ۸.۷ — Data Governance و Privacy

دو ادعای فعلی باید اصلاح شوند ([نقص ۸](#نقص-۸--edge-tts-سرویس-بیرونی-است) و [نقص ۹](#نقص-۹--modelprovider-سراسری-است-نه-per-store)).

راه‌حل: یک **AI/Data Policy Layer**.

برای هر Store قابل تنظیم:

```text
AI Processing Mode:
  [ Local Only            ]  ← هیچ داده‌ای از سرور خارج نمی‌شود
  [ Approved External     ]  ← فقط Providerهای تأییدشده
  [ Hybrid                ]  ← با اعلام شفاف
```

و برای هر Provider ثبت شود: Data Location، Data Retention، Privacy Policy، Allowed Data Types، Encryption، Consent.

`ModelProvider` باید per-store قابل override شود و AI Gateway ([۸.۴](#۸۴--ai-gateway)) موظف باشد سیاست فروشگاه را رعایت کند.

> اگر فروشگاهی `Local Only` انتخاب کرد و مدل محلی در دسترس نبود، Job باید **شفاف fail شود** — نه اینکه بی‌سروصدا به API بیرونی برود.

## ۹. سیستم‌های جدید

### ۹.۱ — تولید تدریجی ویدیو

#### مشکل

```text
Prompt → چند ساعت پردازش → Final Video
```

این برای تجربه‌ی کاربری خطرناک است. مشتری نباید ۳ ساعت صبر کند تا بفهمد خروجی بد است.

#### راه‌حل: Progressive Generation

```text
Generate Segment 01 → QC → Show to Customer → Approve
        ↓
Generate Segment 02 → QC → Show to Customer → Approve
        ↓
       ...
```

کاربر در هر مرحله بتواند: Stop، Reject، Regenerate، Edit Prompt، Change Style، Change Camera، Change Voice، Continue.

#### دو Mode

**Safe Mode** — هر Segment تأیید دستی:

```text
Generate → QC → Show → Approve
```

**Auto Mode** — فقط وقتی کیفیت پایین است متوقف شود:

```text
Generate → QC → Score > Threshold → ادامه‌ی خودکار
                Score < Threshold → توقف و درخواست تأیید
```

Auto Mode پیش‌فرض باشد؛ Safe Mode برای مشتری وسواسی یا محتوای حساس.

#### Scene State — کلید پیوستگی

پیوستگی فعلی فقط با «فریم آخر Segment قبلی» است (بخش ۸ Master Spec). این کافی نیست.

علاوه بر فریم آخر، یک **Scene State** ساختاریافته منتقل شود:

```text
Scene State
├── Characters      (چه کسانی، با چه ظاهری)
├── Objects         (چه اشیایی، با چه رنگ و شکلی)
├── Location
├── Lighting
├── Camera          (زاویه، فاصله، حرکت)
├── Clothing
├── Colors
└── Current Action
```

این State به Prompt Compiler ([۹.۲](#لایه-۱--prompt-compiler)) داده می‌شود و دقیقاً همان چیزی است که مشکل «یکهو همه‌چیز عوض شد» را کنترل می‌کند.

#### قانون هزینه

اگر QC یک Segment را رد کرد، **اعتبار مشتری مصرف نشود**:

```text
Customer Request → Generation → QC
                      ┌──────┴──────┐
                    PASS          FAIL
                      ↓             ↓
              Consume Credit   Refund Credit
```

این باید **یکی از اصلی‌ترین مزیت‌های فنی محصول** باشد. صرفاً Prompt Engineering کافی نیست.

درون یک Segment یا بین دو Segment:

| حرکت | Motion غیرطبیعی، سرعت غیرمنطقی، Warp، Camera Jump |
| زمانی | Flickering، Temporal Inconsistency |
| محیط | تغییر ناگهانی نور، تغییر محیط، تغییر سبک |

```text
             ┌─────────┴─────────┐
             ▼                   ▼
```

#### لایه ۱ — Prompt Compiler

قبل از ارسال، سیستم خودش Prompt را تقویت کند.

کاربر می‌گوید:

> یک خانم محصول را معرفی کند.

Compiler اضافه می‌کند: `consistent character`، `consistent clothing`، `stable environment`، `natural movement`، `continuous motion`، `stable camera`، `realistic physics`، `consistent lighting`، `object permanence`، `no sudden transformation` — به‌علاوه‌ی Scene State از Segment قبلی.

#### لایه ۲ — Vision Controller

بعد از تولید، فریم‌ها استخراج و بررسی شوند:

- **Character Consistency** — آیا شخصیت از فریم اول تا آخر همان است؟ (Face Embedding، Face Landmark، Head Pose)
- **Object Consistency** — شکل/رنگ/اندازه‌ی محصول تغییر کرده؟ ناپدید شده؟ دوباره با شکل متفاوت ظاهر شده؟
- **Environment Consistency** — محیط ناگهان عوض شده؟
- **Motion** — حرکت طبیعی است؟ (Optical Flow، Motion Discontinuity)
- **Temporal Consistency** — فریم N به N+1 پیوسته است؟
- **Physics** — اشیا قوانین فیزیک را رعایت می‌کنند؟
- **Camera** — حرکت دوربین منطقی است؟
- **Artifact Detection** — دست خراب، انگشت اضافی، Morphing، Flickering، Warping

#### Quality Score

برای هر Segment:

```text
Overall Score: 87/100

Temporal Consistency: 92
Object Consistency:   88
Face Consistency:     95
Motion Quality:       81
Visual Quality:       90
Physics:              84
```

آستانه‌ی نمونه:

```text
90-100 → Excellent
80-89  → Good
70-79  → Review
<70    → Regenerate
```

> این اعداد **نمونه‌اند**. باید بعد از بنچمارک واقعی (فاز ۰.۵) تنظیم شوند.

#### قانون محصول: عکس واقعی در انتهای پست

در محتوای بازاریابی محصول، **عکس واقعی خود محصول در انتهای پست/ویدیو قرار بگیرد** تا مشتری دقیقاً همان چیزی را ببیند که می‌خرد.

و پیش از آن، بینایی ماشین + کد کنترل کنند که محتوای تولیدشده **محصول را عوض نکرده باشد** — همان Object Consistency بالا، ولی این‌بار با مرجع مشخص: عکس اصلی محصول از دیتابیس.

### ۹.۳ — موتور تعمیر سه‌سطحی

تشخیص مشکل کافی نیست. سیستم باید تا جای ممکن **خودش تعمیر کند** — و مهم‌تر، **قبل از مصرف دوباره‌ی GPU**.

#### اصل

```text
Problem Detected → Can Code Fix It?
                        ├── YES → Code-based Repair → Recheck
                        └── NO  → AI Regeneration
```

مثال:

```text
Problem: Low Exposure
  → قابل اصلاح الگوریتمی؟ بله
  → Color Engine → Recheck

Problem: Character identity changed
  → قابل اصلاح الگوریتمی؟ نه
  → Regeneration
```

#### سه سطح

**سطح ۱ — کد (ارزان‌ترین)**
FFmpeg، OpenCV، Audio DSP، Color Processing.
برای: نور، رنگ، لرزش، Flicker، نویز، صدا.

**سطح ۲ — Computer Vision**
Face، Object، Motion، Scene، Tracking، Temporal Analysis.
برای تصمیم‌گیری و اصلاح موضعی.

اینجا همان چیزی است که برای نقص‌های جزئی لازم است: اگر همه‌چیز درست بود ولی **یک قسمت کوچک** مشکل داشت (مثلاً انگشت بد درآمده)، کد باید بتواند همان ناحیه را موضعی اصلاح کند (inpaint/patch) به‌جای رندر دوباره‌ی کل Segment. پردازش به‌شدت پایین‌تر می‌آید.

**سطح ۳ — AI (آخرین گزینه)**
فقط وقتی مشکل واقعاً معنایی است: Bad hand غیرقابل‌ترمیم، Wrong object، Identity change، Impossible geometry، Severe artifact.

#### قانون بازتولید

```text
Segment 1 ✓
Segment 2 ✓
Segment 3 ✗   ← فقط این دوباره تولید شود
Segment 4 —
```

هرگز کل ویدیو از ابتدا رندر نشود.

Repair Strategy برای Segment خراب:

```text
Regenerate Segment
    + Reference Frame (فریم آخر Segment قبلی)
    + Scene State
    + Modified Prompt (بر اساس نوع مشکل تشخیص‌داده‌شده)
```

> **این معماری باعث می‌شود AI گران‌قیمت آخرین گزینه باشد، نه اولین گزینه.**

### ۹.۴ — موتور صدا

Audio نباید Feature فرعی باشد. صدای غیرطبیعی حتی یک ویدیوی تصویری عالی را خراب می‌کند.

هدف:

> صدای طبیعی + لحن مناسب + تلفظ درست + Timing دقیق + هماهنگی با اتفاقات ویدیو

#### Pipeline

```text
Script
  ↓
Text Normalizer        (اعداد، تاریخ، مخفف، انگلیسی داخل فارسی)
  ↓
Pronunciation Engine   (نام برند، واژه‌های خاص)
  ↓
Voice Engine
  ↓
Emotion / Style Controller
  ↓
Audio QC
  ↓
Timing / Phoneme Analysis
  ↓
Video Synchronization
  ↓
Final Audio
```

#### Provider-Based

```text
Voice Engine
    ├── Local TTS              ← برای Local Only mode
    ├── Cloud TTS              ← edge-tts فعلی
    └── Future Custom Voice Model
```

انتخاب Engine بر اساس: زبان، جنس صدا، سبک، Emotion، سرعت، کیفیت، هزینه، Hardware، و **Privacy Policy فروشگاه** ([۸.۷](#۸۷--data-governance-و-privacy)).

#### Voice Profile

برای هر صدا: Language، Gender، Age، Accent، Speaking Rate، Pitch، Emotion، Energy، Pause Style.

#### Audio QC

قبل از Final Render ارزیابی شود: Pronunciation، Pauses، Speaking Rate، Pitch Variation، Emotion، Loudness، Clipping، Noise، Robotic Artifacts، Timing.

اگر صدا مصنوعی، بریده‌بریده یا غیرطبیعی بود، سیستم قبولش نکند و دوباره تولید کند.

#### هم‌زمانی صدا و تصویر

```text
Script → Voice Generation → Phoneme / Timing Extraction
→ Speech Timeline
                ↕
        Video Action Timeline
                ↓
        Synchronization Engine
                ↓
          Final Render
```

اگر متن می‌گوید «این محصول را ببینید…»، حرکت و Action باید با Timing صدا هماهنگ باشد.

> **نکته‌ی واقع‌بینانه:** Lip Sync و Viseme Mapping فقط وقتی معنا دارد که **انسان سخنگو** در تصویر باشد. ویدیوهای فعلی محصول (Wan 2.2 i2v روی عکس محصول) گوینده‌ی روی تصویر ندارند و نریشن روی تصویر پخش می‌شود. پس Lip Sync را باید به فازی موکول کرد که «ویدیوی با presenter» جزو محصول شود — نه الان.

### ۹.۵ — موتور تدوین و Post-Production

#### ایده‌ی اصلی

سیستم فقط نباید ویدیو تولید کند. باید بتواند **ویدیو را بفهمد، تحلیل کند، تدوین کند، اصلاح کند و برای انتشار آماده کند.**

دو نوع ورودی:

1. ویدیوهای تولیدشده توسط موتور AI خودمان
2. ویدیوهایی که کاربر آپلود می‌کند

> ⚠️ ورودی نوع ۲ یک **تصمیم استراتژیک** است، نه یک Feature. ببین [تصمیم ۱](#تصمیم-۱--آیا-ادیتور-ویدیوی-کاربر-جزو-این-محصول-است).

### ۹.۶ — ادیتور ایجنتیک

این شاید **مهم‌ترین تصمیم معماری کل پروژه** باشد.

#### اصل

> **مدل ارزان = مغز تصمیم‌گیرنده**
> **Computer Vision = چشم**
> **FFmpeg/OpenCV/Audio/Color = دست**
> **QC = بازرس**
> **مدل گران = متخصص تعمیرات سخت**

لازم نیست یک مدل گران را مجبور کنیم خودش ویدیو را پردازش کند. مدل فقط **تصمیم می‌گیرد چه ابزاری، کجا، با چه پارامتری اجرا شود.**

```text
                    VIDEO
                      ▼
              Video Understanding
                      ▼
              Cheap AI / LLM
             "Editing Director"
                      ▼
             Editing Plan / Commands
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   FFmpeg Tools   OpenCV Tools   CV Tools
        └─────────────┼─────────────┘
                      ▼
                 Video Editor
                      ▼
                     QC
                 ┌────┴────┐
                 ▼         ▼
               PASS      REPAIR
```

#### Tool Registry

```text
VIDEO TOOLS
├── تحلیل:  analyze_video · detect_scene · detect_face · detect_object
│            detect_motion · detect_blur · detect_noise · detect_silence
├── برش:    cut · trim · merge · crop · resize · rotate · speed
├── رنگ:    exposure · brightness · contrast · saturation
│            color_balance · sharpen · denoise
├── حرکت:   stabilize · auto_reframe · smart_zoom
├── متن:    subtitle · caption · watermark · logo
├── صدا:    audio_cleanup · normalize_audio · remove_silence · music_ducking
└── خروجی:  b_roll · transition · render_preview · quality_check
```

#### مدل مستقیم به FFmpeg دسترسی ندارد

این را **انجام نمی‌دهیم**:

```text
LLM → arbitrary shell command
```

به‌جایش:

```text
LLM → Typed Tool API → Validation → Editing Engine → FFmpeg/OpenCV
```

مدل فقط اجازه دارد چنین چیزی بدهد:

```json
{
  "tool": "smart_zoom",
  "parameters": { "start": 10, "end": 15, "scale": 1.08 }
}
```

و Backend قبل از اجرا بررسی کند: پارامتر معتبر است؟ زمان داخل ویدیو است؟ مقدار Zoom مجاز است؟ فایل متعلق به همین Project است؟ عملیات خطرناک نیست؟

**این از نظر امنیت و پایداری الزامی است، نه اختیاری.**

#### حلقه‌ی Observe → Plan → Act → Verify

مدل بعد از هر عملیات دوباره نتیجه را ببیند:

```text
        ┌──────────────────────┐
        ▼                      │
     OBSERVE                   │
        ↓                      │
      PLAN                     │
        ↓                      │
       ACT                     │
        ↓                      │
      VERIFY ───── FAIL ───────┘
        │

        ↓

```

**این از صرفاً «LLM + FFmpeg» خیلی قوی‌تر است.**

#### نمونه — ویدیوی AI خودمان

مدل ویدیو یک Segment ۵ ثانیه‌ای تولید کرده. Computer Vision گزارش می‌دهد:

```text
Lighting       72
Sharpness      91
Face           94
Object         88
Motion         61
Temporal       57
Continuity     63
```

مدل ارزان این گزارش را می‌بیند و تصمیم می‌گیرد:

> Motion و Temporal مشکل دارند؛ Color مشکل ندارد.

پس **فوراً regenerate نمی‌کند**. اول:

```text
stabilize() → deflicker() → motion_smoothing() → QC دوباره
```

و فقط اگر هنوز خراب بود → AI Regeneration.

#### نمونه — ویدیوی خام مشتری

```text
UPLOAD → ANALYZE → CHEAP LLM → EDIT PLAN → TOOLS
→ PREVIEW → QC → REPAIR → FINAL RENDER
```

مشتری لازم نیست بداند پشت صحنه FFmpeg یا OpenCV هست. برای او فقط یک دکمه است: **Auto Edit**.

نمونه‌ی یک Plan برای Reel:

```text
analyze_video → detect_scenes → detect_silence → remove_silence
→ auto_reframe(9:16) → smart_zoom → generate_captions
→ caption_style("reels") → audio_cleanup → color_correct

```

| Mode | رفتار |
|---|---|
| **Manual** | کاربر خودش دستور می‌دهد |

| **Director** | کاربر فقط هدف را می‌گوید: «مثل یک YouTuber حرفه‌ای ادیتش کن، طبیعی باشه و افکت زیاد نداشته باشه» |

### ۹.۷ — Omnichannel Communication

نباید برای هر شبکه یک سیستم جدا و درهم بسازیم.

```text
                 Communication Core
                        │
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
   Messaging         Social           External
       │                │                │
   WhatsApp         Instagram        Public API
   Telegram         Facebook         Webhook
   SMS              ...
   Website
```

هر سرویس Adapter مستقل خودش را داشته باشد (`WhatsAppAdapter`، `TelegramAdapter`، …) ولی همه به **یک Interface مشترک** وصل باشند.

#### Inbox واحد

```text
All Messages
 ├── WhatsApp   ├── Website
 ├── Telegram   ├── SMS
 ├── Instagram  └── External API
```

کاربر بتواند: پیام را ببیند، پاسخ دهد، Conversation را Assign کند، Tag کند، وضعیت را تغییر دهد، Customer Profile و تاریخچه را ببیند، از AI پیشنهاد پاسخ بگیرد، پاسخ خودکار فعال کند.

#### API عمومی

> **⚠️ این بخش یک طرح است، نه توصیف کد.** مسیرهای `/projects/` پایین **ساخته
> نشده‌اند**. آنچه امروز واقعاً وجود دارد، پنج اندپوینت زیر است — با مدیریت
> کلید، سهمیه‌ی مشترک با پنل، و لاگ فراخوانی (`apps/api_platform/`):
>
> ```http
> POST /api/v1/public/sales-agent/
> POST /api/v1/public/caption/
> POST /api/v1/public/video/
> POST /api/v1/public/poster/
> GET  /api/v1/public/showcase/
> GET  /api/v1/public/jobs/{id}/
> ```
>
> این‌ها **قابلیت‌محور**ند نه پروژه‌محور: هر فراخوانی یک کار مشخص می‌خواهد و
> شناسه‌ی Job می‌گیرد. طرح `/projects/` پایین یک مدل متفاوت است — پروژه‌ی
> ادیت با آپلود و رندر — و اگر روزی لازم شد، **کنار** این‌ها ساخته می‌شود نه
> به‌جایشان. صفحه‌ی «کلیدهای API» در پنل، همان پنج‌تای واقعی را با نمونه‌ی
> `curl` نشان می‌دهد.

طرح اولیه (ساخته نشده):

```http
POST /api/v1/projects
POST /api/v1/projects/{id}/upload
POST /api/v1/projects/{id}/analyze
POST /api/v1/projects/{id}/auto-edit
POST /api/v1/projects/{id}/render
GET  /api/v1/projects/{id}/status
GET  /api/v1/projects/{id}/export
```

تا شرکت‌های دیگر بتوانند سیستم خودشان را وصل کنند یا Editor ما را داخل محصول خودشان استفاده کنند.

### ۹.۹ — اشتراک، اعتبار و تضمین کیفیت

#### Payment Gateway — Provider-Based

معماری باید Provider-Based باشد تا بعداً Gateway بدون تغییر منطق Subscription عوض شود.

اجزای لازم:

```text
ایجاد Payment → Callback/Webhook → Verify Payment
→ تمدید خودکار Subscription
```

به‌علاوه: Grace Period، Failed Payment Handling، Invoice/Receipt، Transaction History، Refund، Upgrade/Downgrade، لغو Subscription، محدودیت مصرف بر اساس Plan، Audit Log کامل.

#### Credit Architecture

```text
Customer Credits
       ↓
   Generation
       ↓
      QC
   ┌───┴───┐
 PASS    FAIL
   ↓       ↓
Consume  Refund
Credit   Credit
```

اعتبار مشتری فقط وقتی مصرف شود که عملیات **واقعاً موفق** بوده.

> زیرساخت رزرو/commit/release در `apps/billing/services.py` وجود دارد. کاری که مانده: وصل‌کردنش به Quality Score و Credit model.

#### وقتی مشتری کیفیت را نپسندید

| حالت | رفتار |
|---|---|
| **A — Regenerate** | همان Segment دوباره ساخته شود |
| **B — Change Style** | Camera / Lighting / Motion / Character / Prompt عوض شود |
| **C — Quality Guarantee** | اگر بعد از چند تلاش Threshold نگرفت: «Generation Failed — Credit Returned» |

برای پلن‌های Premium می‌توان **Quality Guarantee** رسمی تعریف کرد. این از نظر اعتماد مشتری بسیار قدرتمند است.

### ۹.۱۲ — هوش فروشگاه: فروش، موجودی و سود واقعی

امروز `apps/analytics` فقط می‌شمارد. این بخش آن را به **علم داده‌ی فروش** تبدیل می‌کند.

#### چیزی که کم است: قیمت تمام‌شده

مدل `Product` قیمت فروش دارد ولی **قیمت تمام‌شده ندارد**. بدون آن هیچ محاسبه‌ی سودی ممکن نیست — فقط گردش مالی محاسبه می‌شود، نه سود.

```text
Selling Price   ← الان هست
Cost Price      ← باید اضافه شود
────────────────────────────
Real Profit     ← تازه آن‌وقت ممکن می‌شود
```

#### خروجی‌ها

| تحلیل | چه می‌گوید |
|---|---|
| پرفروش‌ترین | کدام محصول بیشترین **تعداد** را فروخته |
| سودآورترین | کدام محصول بیشترین **سود** را ساخته — ممکن است همان نباشد |
| نمودار فروش | روند فروش هر محصول در زمان |
| نمودار موجودی | چه چیزی رو به اتمام است، چه چیزی خوابیده |
| مقایسه‌ی محصولات | کنار هم، بر اساس فروش و سود و گردش |

> **نکته‌ی مهم:** «پرفروش‌ترین» و «سودآورترین» معمولاً یکی نیستند. محصولی که زیاد می‌فروشد ممکن است حاشیه‌ی نازکی داشته باشد. فروشگاه‌دار باید هر دو را ببیند.

#### تغذیه به بقیه‌ی سیستم

این داده نباید در یک صفحه بماند:

```text
Sales Data → کدام محصول محتوا لازم دارد؟
           → کدام محصول را ایجنت فروش بیشتر پیشنهاد بدهد؟
           → کدام محصول در کمپین بعدی برود؟
```

### ۹.۱۳ — ترندها و اتصالشان به تولید محتوا

#### جمع‌آوری

ترندهای **ایرانی** و **خارجی** از شبکه‌های اجتماعی و منابع منتشرکننده‌ی ترند.

برای هر ترند: موضوع چیست، چه نوع محتوایی حولش ساخته می‌شود، چقدر داغ است، و از کِی.

#### پیشنهاد — نه فهرست خام

فهرست ترند به‌تنهایی بی‌فایده است. سیستم باید ترند را با فروشگاه جوش بدهد:

```text
     +

     +

     ↓
«برای محصول X، این ویدیو را با این زاویه بساز»
```

#### اتصال مستقیم

کاربر باید از همین صفحه یک ترند را انتخاب کند و **مستقیم وارد تولید محتوا شود** — اطلاعات ترند همراهش منتقل شود:

```text
Trend → Select Trend → Select Product → Content Generation
```

> **قانون صداقت:** ترند باید از منبع واقعی بیاید با تاریخ و لینک — نه اینکه مدل از خودش «ترند» دربیاورد. همان قانونی که برای تحلیل رقبا داریم.

### ۹.۱۴ — دو حالت تولید: ساده و پیشرفته

#### حالت ساده

از چیزی که **از قبل داریم** استفاده می‌کند:

```text
Product Information + Additional Prompt + Optional Trend → Generate
```

کاربر چیز جدیدی نمی‌دهد. سریع است و برای بیشتر موارد کافی.

#### حالت پیشرفته

سیستم **تشخیص می‌دهد چه چیزی کم دارد و می‌پرسد**:

```text
Trend / Reference
     ↓
AI Analysis
     ↓
«برای این خروجی، عکس محصول از زاویه‌ی روبه‌رو لازم دارم»
     ↓
User Provides Image / Video / Info
     ↓
Generation → Caption → Advanced Editing → Final
```

تفاوت اصلی: **پیشرفته ورودی بیشتری می‌خواهد تا خروجی خاص‌تر و باکیفیت‌تر بدهد.**

#### دو نوع خروجی تصویر — صریح و جدا

| حالت | برای چه | قانون |
|---|---|---|
| **پوستر / بیلبورد** | کمپین، تبلیغ، پیشنهاد ویژه | AI طرح می‌سازد، **کد متن را می‌نشاند** |
| **نمایش محصول** | پست، استوری، معرفی | **محصول واقعی باید حفظ شود** |

در حالت نمایش محصول، AI اجازه دارد مدل، محیط، نور، پس‌زمینه و ترکیب‌بندی را عوض کند — **ولی خود محصول را نه**.

### ۹.۱۷ — بازاریابی تلفنی

> **وضعیت (۱۴۰۴/۰۶/۳۰): بخش عمده‌اش ساخته شد.** فهرست و پیگیری، ضبط و تحلیل
> تماس، و آماده‌سازی قبل از تماس کد دارند. یک بند از زنجیره‌ی زیر عمداً ساخته
> نشد — «از روی شماره دنبالش بگرد» — و دلیلش پایین آمده.

#### زنجیره

```text
شماره یا نام شرکت
     ↓
Customer / Company Research     ← پیدا کردن پروفایل و راه ارتباطی
     ↓
ارتباط اولیه                    ← پیام یا تیکت
     ↓
Mobile Call Assistant          ← موقع تماس، پروفایل را نشان می‌دهد
     ↓
Real-Time Sales Assistant      ← در لحظه پیشنهاد می‌دهد چه بگوید
     ↓
Call Recording & Analysis
     ↓
Post-Call Analysis             ← استخراج اطلاعات → به‌روزرسانی پروفایل
```

#### تحقیق شرکت

از نام یا سایت شرکت: راه‌های ارتباطی، HR، مارکتینگ، فروش، و **افراد تصمیم‌گیرنده**.

#### ⚠️ دو قیدی که تکلیفشان روشن شد — و جوابشان یکی نبود

**۱. قانونی بودن ضبط تماس — ✅ حل شد، با ساختنش.**
قید درست بود و جوابش «نساختن» نبود: آنچه کم بود خودِ **رضایت** بود، نه ضبط.
حالا `CallConsent` یک ردیف است که می‌گوید چه کسی، کِی، و **دقیقاً چطور** رضایت
داد — متن آزاد و اجباری، چون یک تیکِ تنها چیزی تولید می‌کند که از رضایتِ
واقعاً گرفته‌شده قابل تشخیص نیست. و قانون در `Recording.save` نشسته نه در فرم:
بدون ردیف فعال، فایل ذخیره نمی‌شود — از API، از ادمین، از شل، از هیچ‌جا.
رضایت پس‌گرفتنی است و ضبط‌های قبلی می‌مانند، چون وقتی گرفته شدند قانونی بودند.

**۲. جمع‌آوری اطلاعات شخصی — ✅ حل شد، با نساختنش.**
«شماره را بده تا در تلگرام و شبکه‌ها دنبالش بگردیم» یک مسئله‌ی رضایت نیست که
فرم حلش کند: این پیدا کردن حساب‌های کسی است که با این فروشگاه هیچ رابطه‌ای
ندارد — مکانیزم آزار آدم‌ها، و فقط با سوءاستفاده از API پلتفرم‌ها ممکن.
**ساخته نشد و کلیدی هم برای روشن کردنش نیست.**
آنچه واقعاً لازم بود ساخته شد: `match_known_contact` جواب می‌دهد «این شماره را
از قبل می‌شناسیم؟» — فقط از روی مشتری‌ها و سرنخ‌های خودِ همان فروشگاه.

> **درسی که این دو با هم می‌دهند:** «قید حقوقی» دو چیز کاملاً متفاوت را یک
> اسم صدا می‌زد. یکی‌اش قابلیتی بود که ساخته نشده بود؛ دیگری کاری بود که
> نباید بشود. تا وقتی هر دو زیر «معلق» بودند، هیچ‌کدام تکان نمی‌خورد.

- قیمت **هاردکد نشود** — از بک‌اند بیاید تا سایت و محصول هرگز اختلاف نداشته باشند.
- فرم تماس **واقعی** باشد، نه `mailto:` و نه فرم ظاهری.
- تگ‌های کم‌محتوا **ایندکس نشوند**.
- نمونه‌کار ساختگی به‌عنوان مشتری واقعی نمایش داده نشود.
- ادعای غیرقابل‌اثبات درباره‌ی افزایش فروش نوشته نشود.
- Schema فقط وقتی استفاده شود که با محتوای واقعی صفحه بخواند.

## ۱۰. تصمیم‌های باز

این‌ها را کد نمی‌تواند جواب بدهد. باید تصمیم گرفته شود.

### تصمیم ۱ — آیا ادیتور ویدیوی کاربر جزو این محصول است؟

محصول فعلی ICP مشخصی دارد: **صاحب فروشگاه آنلاین**. مدل مالی، سه پکیج، و کل ارائه روی همین بسته شده.

ولی موتور تدوین ([۹.۵](#۹۵--موتور-تدوین-و-post-production)) مخاطب دیگری را هدف می‌گیرد: یوتیوبر، تولیدکننده‌ی محتوا، اینفلوئنسر، مدرس، پادکستر، آژانس تبلیغاتی.

این‌ها **بازار متفاوت، قیمت‌گذاری متفاوت، رقبای متفاوت** دارند.

| گزینه | یعنی |
|---|---|
| **الف** | موتور تدوین فقط داخلی باشد — برای بهتر کردن ویدیوی خودمان. ICP عوض نمی‌شود. |
| **ب** | ادیتور به‌عنوان قابلیت جانبی به همان فروشگاه‌دارها داده شود (ویدیوی موبایلی خودشان را حرفه‌ای کند). |
| **ج** | ادیتور محصول دوم و مستقل شود، با ICP و قیمت خودش. |

**پیشنهاد:** الف در فاز اول (چون موتورش برای QC و تعمیر لازم است)، ب بعد از تثبیت، ج فقط اگر داده‌ی بازار پشتیبانی کند.

### تصمیم ۲ — LLM روی GPU یا API؟

اگر متن و تحلیل به API برود ([۸.۴](#۸۴--ai-gateway))، GPU آزاد می‌شود و مدل ظرفیت واقعی می‌شود. ولی:

- قول «داده‌ی شما پیش ما می‌ماند» باید بازنویسی شود، یا حالت Local Only واقعاً پیاده شود.
- هزینه‌ی متغیر هر مشتری بالا می‌رود و باید در `data.json` وارد شود.

**پیشنهاد:** Hybrid با انتخاب فروشگاه — و اثر هزینه‌اش صریح در مدل مالی.

### تصمیم ۳ — پرداخت اول یا کیفیت اول؟

**پیشنهاد:** کیفیت اول، ولی نه به قیمت بی‌نهایت. تا ~۲۰ مشتری اول، فعال‌سازی دستی اشتراک قابل تحمل است؛ **دیپلوی و دیتابیس** قابل تعویق نیستند.

ترتیب: بنچمارک → زیرساخت → کیفیت تولید → پرداخت → بقیه.

### تصمیم ۴ — سخت‌افزار

با شواهد [نقص ۵](#نقص-۵--مدل-روی-سختافزار-جا-نمیشود)، دو RTX 3060 12GB برای اجرای همزمان qwq:32b و Wan 2.2 کافی نیست.

گزینه‌ها: کارت با VRAM بیشتر / مدل کوچک‌تر برای reasoning / انتقال reasoning به API / تفکیک نقش کارت‌ها (یکی LLM، یکی رندر).

این تصمیم باید **بعد از بنچمارک فاز ۰.۵** گرفته شود، نه قبلش.

### فاز ۱۸ — Production Foundation

مرجع: [۸.۲](#۸۲--دیتابیس-و-ذخیرهسازی) · [۸.۳](#۸۳--زیرساخت-production) · [۸.۴](#۸۴--ai-gateway) · [۸.۷](#۸۷--data-governance-و-privacy)

- [x] **PostgreSQL برای Production** ✅ — با `DATABASE_URL`؛ خالی بگذاری SQLite می‌ماند.
  اسکیم غیر از postgres رد می‌شود، رمز URL-encoded درست decode می‌شود،
  `CONN_MAX_AGE` تا اتصال به‌ازای هر درخواست باز نشود. SQLite دِو هم WAL و
  busy_timeout گرفت تا کمی شبیه production رفتار کند.
- [x] **Dockerfile + docker-compose + Nginx** ✅ — ۹ سرویس:
  db · redis · migrate · backend · worker-ai · worker-gpu · website · nginx · backup
  - ایمیج‌ها multi-stage و **non-root**؛ کامپایلر در لایه‌ی runtime نمی‌ماند.
  - `migrate` سرویس جداست، نه entrypoint — وگرنه هر replica هم‌زمان روی یک
    دیتابیس migrate می‌زند.
  - `worker-gpu` با `concurrency=1` چون یک کارت بیشتر نیست؛ `worker-ai` جداست
    تا رندر ۴۰ دقیقه‌ای کپشن‌ها را پشت خودش نگه ندارد.
  - redis با `appendonly` تا ری‌استارت، صف رندرها را بی‌صدا دور نریزد.
  - nginx یک مبدأ برای همه‌چیز می‌سازد و `X-Forwarded-For` واقعی را پاس می‌دهد
    (اندپوینت لید برای تشخیص سوءاستفاده رویش حساب کرده).
- [x] **Backup + مستند Deployment** ✅ — دامپ شبانه روی هاست (نه داخل ولوم، تا
  بازیابی به زنده بودن کانتینر وابسته نباشد)، اول `.partial` بعد rename چون
  فایل نیمه‌نوشته با نام واقعی از نبودن بکاپ بدتر است.
- [x] **گاردهای production** ✅ — بالا نمی‌آید اگر: `SECRET_KEY` پیش‌فرض باشد،
  `ALLOWED_HOSTS=*` باشد. و اگر `DATABASE_URL` خالی باشد هشدار SQLite می‌دهد.
- [x] **AI Gateway** ✅ — `services/ai/gateway.py`، تنها درِ بین منطق کسب‌وکار و
  هر سرویس هوش مصنوعی.
  - `factory.text_provider()` بدون فروشگاه **حذف شد**، نه اینکه منسوخ اعلام شود.
    همان تابع بود که اجازه می‌داد یک سوییچ پلتفرم‌واید، دادهٔ یک فروشگاه را
    جابه‌جا کند بی‌آنکه صاحبش بداند. حالا امضای گیت‌وی `store` را **اجباری**
    می‌گیرد: تماسی که نمی‌تواند بگوید دادهٔ چه کسی را حمل می‌کند، حق زدنش را ندارد.
  - قانون با **تست** نگه داشته می‌شود نه با یادداشت: `tests_boundary.py` درخت
    `apps/` را AST-پارس می‌کند و اگر ماژولی مستقیم `ollama` یا `openai_compat`
    یا `factory` را ایمپورت کند، بیلد قرمز می‌شود. دو صفحهٔ ادمینِ خودِ
    سرویس‌دهنده‌ها با دلیل استثنا شده‌اند.
- [x] **Data Policy Layer** ✅ — `StoreAIPolicy` per-store با سه حالت.
  - `Local Only` یعنی **کار با پیام روشن fail می‌شود**، نه اینکه بی‌صدا به API برود.
  - دو دروازهٔ مستقل برای دادهٔ مشتری: اپراتور باید سرویس را برای نوع دادهٔ
    `CUSTOMER` مجاز کرده باشد **و** مالک فروشگاه صریحاً اجازه داده باشد. پیام
    خصوصی مشتری، دادهٔ خودِ اوست نه فروشگاه؛ پیش‌فرض خاموش است.
  - سرویس بیرونی که تیک «تأییدشده» بخورد، تا نگوید داده کجا پردازش و چقدر
    نگه‌داری می‌شود ذخیره نمی‌شود — وگرنه «تأیید» فقط یک مهر لاستیکی است.
  - کارت پنل (`DataPolicyCard`) هم تنظیم را می‌دهد هم **می‌گوید چه چیزی با آن
    از کار می‌افتد**؛ تنظیمی که بگوید «فقط لوکال» ولی نگوید صداگذاری قطع می‌شود، تله است.
- [x] **اصلاح ادعای Privacy** ✅ — «داده‌ی شما پیش ما می‌ماند، نه سرویس خارجی»
  با کد نمی‌خواند: edge-tts متن نریشن را به مایکروسافت می‌فرستد و تحقیق رقبا
  دیجی‌کالا/ترب را می‌خواند. متن سایت و `data.json` هر دو به همان چیزی که
  واقعاً اتفاق می‌افتد اصلاح شدند. `get_tts_provider` هم حالا سیاست فروشگاه را
  چک می‌کند و برای فروشگاه «فقط لوکال» صدا **تولید نمی‌کند**.
- [x] Object Storage جدا از دیتابیس — `MEDIA_STORAGE=s3` با هر ارائه‌دهنده‌ی S3-سازگار (آروان، لیارا، MinIO). با فاز ۲۳ لازم شد، چون ویدیوی آپلودی مشتری دیگر چیزی نیست که بشود دوباره ساختش
- [x] Monitoring — `/healthz` (زنده‌ام؟ هیچ چیزی را لمس نمی‌کند)، `/readyz` (می‌توانم سرویس بدهم؟ دیتابیس و صف)، `/metrics` (عمق صف، نرخ شکست، کارهای گیرکرده، وضعیت موتورها)

> **اگر `MEDIA_STORAGE=s3` باشد و کتابخانه یا کلیدها نباشند، سرور بالا نمی‌آید.** رد شدن بی‌صدا یعنی فایل‌ها روی ولوم کانتینر نوشته می‌شوند و اولین دیپلوی بعدی همه‌ی ویدیوهای رندرشده را با خودش می‌برد.
>
> **کارِ منتظر تأیید، کارِ گیرکرده نیست.** یکی سالم است و منتظر آدم؛ شمردنش به‌عنوان مشکل باعث می‌شود یک قابلیتِ درست، هر روز شبیه قطعی به نظر برسد.
>
> **شبِ خلوت، نرخ موفقیت ۱۰۰٪ نیست.** وقتی هیچ کاری اجرا نشده، `failure_rate` برابر `null` است نه صفر — عددی که کسی در جلسه نقلش کند نباید از تقسیم بر هیچ آمده باشد.

**DoD:** کل استک روی یک سرور تمیز با `docker compose up` بالا می‌آید، بدون هیچ وابستگی به سیستم شخصی. فروشگاهی که `Local Only` انتخاب کند، Jobش در نبود مدل محلی **شفاف fail شود** — نه اینکه بی‌سروصدا به API بیرونی برود.

> **🐛 سه ناهماهنگی که فقط موقع نوشتن دیپلوی پیدا شدند** — هیچ‌کدام در تست یا بیلد دیده نمی‌شدند:
> ۱. کامپوز `CELERY_BROKER_URL` می‌داد ولی settings فقط `REDIS_URL` می‌خواند —
>    ورکرهای دیپلوی‌شده بی‌صدا به localhost برمی‌گشتند و بروکری پیدا نمی‌کردند.
> ۲. `CSRF_TRUSTED_ORIGINS` اصلاً تنظیم نمی‌شد — پشت پروکسی TLS، لاگین ادمین ۴۰۳
>    می‌داد و شبیه رمز اشتباه به نظر می‌رسید. `SECURE_PROXY_SSL_HEADER` هم اضافه شد.
> ۳. بیلد standalone سایت، خروجی را در `.next/standalone/Desktop/upM/.../server.js`
>    می‌گذاشت چون Next ریشه‌ی ردیابی را از مسیر مطلق حدس می‌زد —
>    `COPY` داکرفایل چیزی پیدا نمی‌کرد. با `outputFileTracingRoot` پین شد.
>
> **⚠️ آنچه تأیید نشده:** داکر روی این سیستم نصب نیست، پس **ادعا نمی‌کنم استک
> بالا می‌آید**. تأییدشده: YAML معتبر، وابستگی سرویس‌ها درست، تنظیمات با
> `DATABASE_URL` واقعی PostgreSQL می‌سازد، گاردها واقعاً جلوی بالا آمدن را
> می‌گیرند، و بیلد standalone اجرا شد و روی پورت ۲۰۰ داد.
> اولین `docker compose up` باید روی سرور انجام شود.

> 🐛 **باگی که فقط اجرای واقعیِ DoD پیدا کرد — و مهم‌تر از خودِ فاز است:**
> برای اثبات DoD یک اجرای واقعی گذاشتم: فروشگاهی با سیاست `Local Only` و تنها
> یک سرویس بیرونی. حالت `Local Only` درست fail شد، ولی حالت `Hybrid` هم fail
> شد — با این خطا:
>
> ```
> OpenAICompatProvider.generate_json() takes 2 positional arguments but 3 were given
> ```
>
> یعنی **مسیر «متن را به API بدهیم» هیچ‌وقت کار نمی‌کرد.** `_single_call` مدل را
> positional می‌دهد و `(parsed, raw)` را unpack می‌کند؛ نسخهٔ API مدل را
> keyword-only می‌گرفت و فقط یک dict برمی‌گرداند. هیچ تستی نگرفته بود چون هر
> تستِ آن لایه، provider را mock می‌کند — mock هر امضایی را قبول می‌کند.
>
> **چرا این مهم است:** [۸.۴](#۸۴--ai-gateway) همین مسیر را راه‌حل مشکل ظرفیت
> GPU می‌داند. اگر روز شلوغی می‌خواستیم متن را به API منتقل کنیم تا GPU فقط
> برای رندر بماند، با TypeError روبه‌رو می‌شدیم — نه در تست، که در production.
>
> امضا و نوع خروجی هم‌تراز شد و `ProviderContractTests` اضافه شد که امضای دو
> provider را با `inspect` مقایسه می‌کند و یک بار هم دقیقاً همان تماسی را که
> `_single_call` می‌زند اجرا می‌کند. اجرای دوباره: `Hybrid` واقعاً به شبکه رسید
> (DNS دامنهٔ ساختگی شکست) و `Local Only` قبل از هر تماس شبکه‌ای متوقف شد.
>

    قابلیتی که زیر موفقیت ملایم سایت را می‌خواباند باارزش‌تر است.**

> **بازسازی موتور صدا (۱۴۰۵/۰۶/۳۰) — همه از جنگو ادمین سوییچ می‌شود.**
> جدول «موتورهای صدا» (`AudioEngine`) سه نقش دارد و هر نقش چند موتور لوکال و
> API؛ «فعال» و «اولویت» تعیین می‌کند کدام اول امتحان شود و اگر کار نکرد بعدی
> جایش را بگیرد. دکمه‌ی «آزمایش» نمونه‌ی واقعی می‌سازد. سیاست «فقط لوکال»
> فروشگاه فقط موتورهای لوکال را می‌بیند.
>
> - **گوینده:** Piper (آفلاین روی CPU، رایگان)، Edge، Azure، هر API سازگار با
>   OpenAI (`/v1/audio/speech`)، ElevenLabs، gTTS. وضوح با Whisper اندازه گرفته
>   شد (درصد خطای حروف، کمتر بهتر): Edge فرید ۱۱.۷، دلارا ۱۲.۵، Piper gyro ۱۷.۲،
>   ganji ۱۸.۹، amir ۲۱.۸، reza ۲۴.۳. پیش‌فرض: Edge، و Piper gyro (MIT) پشتش
>   برای روز بی‌اینترنت. سرعت Piper روی همین CPU: ۸ ثانیه صدا در کمتر از یک
>   ثانیه. صدای زن فارسی آفلاین با کیفیت قابل قبول هنوز وجود ندارد.
> - **پرداخت صدا** (`polish.py`): حذف غرش، کم‌کردن گلی، وضوح، نرم‌کردن «س/ش»،
>   فشرده‌سازی ملایم، بلندی ۱۶- LUFS، ۴۸ کیلوهرتز — روی خروجی همه‌ی موتورها.
> - **صدای محیط و افکت** (`soundscape.py`): ۱۳ صدای محیط (باران، باد، دریا،
>   طبیعت، خیابان، کافه، آشپزخانه، فروشگاه، دفتر، شب، شومینه، آب، اتاق) و ۱۳
>   افکت (قدم، کفش پاشنه‌دار، در، ووش، شاتر، پارچه، زیپ، ریختن، لیوان، تایپ،
>   کاغذ، اسپری، کلید برق). منبع: کتابخانه‌ی **ضبط‌های واقعی CC0 از Freesound**
>   که یک بار دانلود و بعد آفلاین است؛ برای صداهای نویزمانند ساخت با کد؛
>   جست‌وجوی زنده؛ یا ElevenLabs. سناریو (پرامپت v5) برای هر صحنه صدای محیط و
>   افکت را انتخاب می‌کند؛ اگر نکرد، از کلمه‌های خود صحنه. صحنه‌های پشت‌سرهم با
>   یک صدای محیط، یک بستر پیوسته می‌گیرند؛ روی برش NEW_SCENE یک «ووش» ملایم.
> - **سلسله‌مراتب بلندی** (`AudioMix` در ادمین): گوینده ۱۶-، افکت ۲۶-، صدای
>   محیط ۳۶-، پس‌زمینه‌ی آپلودی فروشگاه ۳۸- LUFS با سقف ۳۰-؛ همه زیر صدای
>   گوینده پایین می‌آیند.
> - **حذف نویز** (`denoise.py`): DeepFilterNet، RNNoise (مدل همراه پروژه)،
>   noisereduce، FFT. روی صدای گوینده در نویز خیابان و وزوز برق: نسبت صدا به
>   نویز ۲۶ → ۴۲ (DeepFilterNet)، ۳۷ (RNNoise)، ۳۸ ولی صدای گوینده ۵ دسی‌بل ضعیف
>   شد (noisereduce)، ۲۸ (FFT). تحلیل ویدیوی آپلودی نویز را خودش اندازه می‌گیرد
>   و زیر ۳۰ دسی‌بل «حذف نویز» را پیشنهاد می‌کند؛ ابزار ادیتور از موتور ادمین
>   استفاده می‌کند و نتیجه در «قبل و بعد» دیده می‌شود.
> - **دو باگ QC صدا که پیدا و رفع شد:** جمله‌ی کوتاه در صحنه‌ی بلند (۲۶٪ زمان)
>   «شنیده نمی‌شود» حساب می‌شد و بی‌دلیل دوباره ساخته می‌شد؛ حالا سهم حرف نسبت
>   به طول متن سنجیده می‌شود. Piper بلافاصله بعد از آخرین کلمه تمام می‌شد و QC
>   آن را «قطع‌شده» می‌دانست؛ حالا یک مکث طبیعی پایانی دارد.
> - **راه‌اندازی:** `python manage.py audio_setup` صداهای Piper، DeepFilterNet
>   و کتابخانه را یک‌بار دانلود می‌کند؛ `start.bat` اگر کم باشند می‌پرسد.
>   مدل‌ها در `Code/UpMarket/models/` (خارج از گیت، مثل ffmpeg)، کتابخانه در
>   `media/sound_library/` (داخل گیت).
> - **بعد از بازبینی مستقل (۱۲ ایراد، همه رفع شد):** مدل خراب Piper حالا به
>   موتور بعدی می‌رسد و هر صدا با تنظیم خودش خوانده می‌شود (انگلیسی ۱۱٪ کندتر
>   از حد می‌خواند)؛ سیاست «فقط لوکال» در صورت خطا سخت‌گیر است؛ حذف نویز با
>   لب‌ها هم‌زمان می‌ماند (جابه‌جایی ۰ میلی‌ثانیه، استریو حفظ می‌شود)؛ ویدیوی
>   فقط‌موسیقی دیگر «پرنویز» تشخیص داده نمی‌شود (Silero VAD)؛ صدای محیط بدون
>   افت در نقطه‌ی تکرار حلقه می‌شود (قبلاً ۲۰ تا ۴۰ دسی‌بل افت در هر دور)؛
>   کتابخانه روی S3 هم کار می‌کند؛ صدای «کافه‌ی دنج» دیگر «شومینه» انتخاب
>   نمی‌شود؛ و صدای گوینده دو بار کمتر فشرده (AAC) می‌شود.
> - **در فرانت هم (همان روز):** تب «صدا و گوینده» در تنظیمات فروشگاه (مرد/زن،
>   سرعت و زیروبمی، «بشنو» با همان موتور واقعی، فهرست تلفظ اسم‌ها، و این‌که کدام
>   موتور آنلاین یا آفلاین می‌خواند)؛ ستون «صدای محیط و افکت» برای هر صحنه در
>   استودیوی ویدیو؛ نمره‌ی کیفیت گوینده و هشدارها کنار ویدیو؛ در ویرایشگر، دکمه‌ی
>   «حذف نویز صدا»، افزودن دستی هر ابزار (حالت «دستی» تا حالا عملاً کار نمی‌کرد) و
>   گزارش موتور حذف نویز. `start.bat` حالا همه‌ی صداهای Piper که ردیف‌های ادمین
>   نام برده‌اند را هم دانلود می‌کند، با آینه‌ی Hugging Face. یک باگ جدی هم پیدا شد:
>   متد `check` دستور `audio_setup` هم‌نام قلاب سیستمی جنگو بود، پس روی سیستم تازه
>   دانلود هیچ‌وقت شروع نمی‌شد.
> - **هم‌زمانی صدا با تصویر (همان روز، اندازه‌گیری‌شده):**
>   - **افکت روی لحظه‌ی اتفاق** (`services/audio/sync.py`): حرکت دوربین حذف و
>     حرکت موضعی (در، دست، اسپری) در فریم‌های واقعی پیدا می‌شود؛ ضربه‌ی خود صدا
>     روی همان فریم می‌نشیند. خطا در خروجی نهایی: در +۵ میلی‌ثانیه، هر قدم +۵ تا
>     +۶ (حد تشخیص ITU-R BT.1359: صدای زودتر از ۴۵ میلی‌ثانیه). صدای قدم به
>     قدم‌های جدا بریده و هر کدام روی یک قدم تصویر گذاشته می‌شود. یک باگ قدیمی هم
>     رفع شد: میکس تک‌ورودی تأخیر افکت را گم می‌کرد و آن را در ثانیه‌ی صفر پخش می‌کرد.
>   - **لب ناهماهنگ:** «دهان بسته» در پرامپت صحنه‌های آدم‌دار (در پرامپت مثبت، چون
>     Wan با cfg=1 پرامپت منفی را نادیده می‌گیرد)، و بررسی حرکت لب در کنترل کیفیت
>     (`services/video/mouth.py`) که صحنه‌ی لب‌زن را با علت TALKING دوباره می‌سازد.
>     روی پرتره‌ی واقعی با دهان مصنوعی: ۵ از ۵ درست (حرف زدن، حرف زدن ملایم؛ ساکن،
>     پلک، سر تکان دادن رد نشدند). آستانه‌ها باید روی خروجی واقعی Wan دوباره سنجیده شود.
>   - **لب‌خوانی واقعی** (`services/video/lipsync.py`، LatentSync 1.6 روی ComfyUI):
>     کلید «لب‌خوانی» برای هر صحنه، نصب نود و مدل ۵ گیگابایتی در start.bat
>     (`manage.py lipsync_setup`). روی ComfyUI شبیه‌سازی‌شده آزمایش شد؛ روی GPU
>     واقعی هنوز نه.
>   - **نریشن هم‌زمان با محصول** (`services/audio/timing.py`): لحظه‌ی ظاهر شدن
>     محصول با تطبیق عکس محصول (ORB) و لحظه‌ی گفتن اسمش با Whisper پیدا می‌شود و
>     نریشن داخل همان صحنه جابه‌جا می‌شود (در آزمایش: ۱.۴ ثانیه، به اندازه‌ی جای
>     خالی صحنه). مدل Whisper هم به دانلودهای start.bat اضافه شد.
> - **کارهای باز بعد از کامیت (همان روز، اندازه‌گیری‌شده):**
>   - **امنیت:** هر عضو فروشگاه (حتی «بازدیدکننده») می‌توانست فروشگاه را تغییر دهد
>     یا **حذف** کند و توکن نوین‌هاب و راز وب‌هوک را ببیند. حالا تغییر فقط با
>     نقش مدیر/مالک، حذف فقط مالک، و توکن‌ها از پروفایل بیرون نمی‌آیند.
>   - **آشکارساز چهره YuNet** (OpenCV، ۲۳۰ کیلوبایت، MIT، داخل پروژه) به جای Haar:
>     روی ۵ تصویر با جواب معلوم ۵ از ۵ درست در برابر ۱ از ۵. بررسی لب حالا پنجره‌ی
>     دهان را از گوشه‌های لب (نقاط چهره‌ی YuNet) می‌سازد؛ ۵ از ۵.
>   - **صدای زن فارسی آفلاین:** Mana (MIT، دیتاست CC-0 ManaTTS). گام صدا ۲۲۰ هرتز
>     (زن)، خطای Whisper ۲۴.۶٪ (دیلارای آنلاین ۱۲.۵٪) — پس پشتیبان آفلاین و صدای
>     «فقط لوکال»، نه اولویت اول.
>   - **نوردهی خودِ محصول** (`services/video/product_region.py`): محصول با عکسش در
>     فریم پیدا و روشنایی‌اش نسبت به همان عکس سنجیده می‌شود؛ محصول روشن روی زمینه‌ی
>     سیاه دیگر «تاریک» حساب نمی‌شود، محصول تاریک روی زمینه‌ی سفید گرفته می‌شود.
>   - **«محصول عوض شده» بدون GPU:** رنگ محصول در برابر عکسش و تناسبش در طول کلیپ؛
>     بدون تغییر ۱.۴، رنگ عوض‌شده ۴۵، تناسب عوض‌شده ۳۰٪.
>   - **فریم شروع صحنه‌ی بعد** (`services/video/anchor.py`): از ۸ فریم آخر، واضح‌ترین؛
>     کلیپ دقیقاً روی همان فریم تمام می‌شود (۳ فریم محو آخر حذف شد، کلیپ سالم دست نخورد).
>   - **اصلاح هر نما جدا در ویدیوی آپلودی:** مرز نماها پیدا و هر نما جدا سنجیده
>     می‌شود؛ اصلاح فقط روی نمای مشکل‌دار با بازه‌ی زمانی. آزمایش: نمای تاریک
>     ۳۰←۱۰۲، نمای سالم دقیقاً بی‌تغییر، رنگ‌زدگی نمای سوم ۳۱←۰.

> **با ffmpeg واقعی اندازه‌گیری شد، نه فقط رندر شد:** موقع حرف‌زدن موسیقی **۹.۹ دسی‌بل** پایین می‌آید و در سکوت‌ها دست‌نخورده برمی‌گردد. این تفاوت مهم است — یک فیلترگراف می‌تواند بی‌عیب باشد، فایل بسازد، صفر برگرداند و **هیچ کاری نکند**؛ اولین اندازه‌گیری من دقیقاً همین را نشان داد و فقط مقایسه‌ی سطح صدا معلوم کرد که کار می‌کند. `services/tests_ffmpeg_real.py` همین را می‌سنجد.
>
> **فایل موسیقی از Openverse می‌آید، فهرست رسمی Creative Commons** — چون مجوز و **متن دقیق ذکر منبع** را همراه هر آهنگ می‌دهد. کتابخانه‌ای که فقط MP3 بدهد و مجوزش را نه، مشکل را به فروشگاه‌دار منتقل کرده است. آهنگ‌های `NC` (غیرتجاری) و `ND` (بدون اثر مشتق) **اصلاً نشان داده نمی‌شوند**: ویدیوی تبلیغاتی فروشگاه دقیقاً استفاده‌ی تجاری است، و کسی که فهرست «موسیقی رایگان» را می‌بیند نمی‌ایستد این را حساب کند. هشدار روی دکمه‌ی دانلود، هشداری است که کسی نمی‌خواند.

> **سه‌تا از پنج تنظیمِ خواسته‌شده برای فارسی وجود ندارند، و صفحه همین را می‌گوید.** قبل از ساختن فرم، از موتور صدا پرسیدم چه دارد:
>
> ```
> fa-IR-DilaraNeural   Female   Friendly, Positive
> fa-IR-FaridNeural    Male     Friendly, Positive
> ```
>
> **دو صدای فارسی وجود دارد. کل کاتالوگ همین است.** هر دو بزرگسال، هر دو تهرانی، هر دو با یک شخصیت. پس **سن** ممکن نیست (صدای کودک یا سالمند فارسی نداریم)، **لهجه** ممکن نیست (یک گویش `fa-IR`)، و **احساس** ممکن نیست (برچسب سبک روی هیچ‌کدام از دو صدا نیست و `edge_tts.Communicate` اصلاً پارامتر سبک ندارد).
>
> آنچه واقعی است اندازه‌گیری شد: `-25%` سرعت یک جمله‌ی ۳.۴۳ ثانیه‌ای را به ۴.۵۴ ثانیه برد، و `+15Hz` انرژی بالای ۲۰۰ هرتز را ۰.۸ دسی‌بل بالا برد.
>
> آن سه تا **با دلیلشان در پنل نوشته می‌شوند**، نه اینکه به‌صورت منوی کشویی بیایند و کاری نکنند. فروشگاهی که «احساس: هیجان‌زده» را می‌گذارد و هیچ تفاوتی نمی‌شنود، یاد گرفته که تنظیمات ما تزئینی‌اند — و این از نبودِ خود قابلیت گران‌تر تمام می‌شود.

> **ویسپر روی سیستم خودمان اجرا می‌شود و این جزئیات نیست.** موتور صدا بیرونی است (edge-tts متن را به مایکروسافت می‌فرستد) و فروشگاهِ «فقط لوکال» اصلاً نمی‌تواند از آن استفاده کند. ویسپر برعکس است — پس سخت‌گیرترین فروشگاه از نظر حریم خصوصی هم می‌تواند ویدیوی خودش را زیرنویس کند، حتی اگر نتواند نریشن بسازد.

> **فایل موسیقی نمی‌دهیم، فقط موتورش را.** تراکی که مجوزش کامل نباشد، استریک کپی‌رایت روی صفحه‌ی **مشتری** می‌آورد — روی ویدیویی که **خودش** منتشر کرده، هفته‌ها بعد، بدون توضیحی که بشود کاریش کرد. پس فروشگاه فایل خودش را می‌گذارد و پنل بالای دکمه‌ی آپلود همین را می‌نویسد، نه در شرایطی که کسی نمی‌خواند.

> **تلفظ عمداً نمره نمی‌گیرد.** بین یک کلمه‌ی درست‌تلفظ‌شده و غلط‌تلفظ‌شده هیچ تفاوت سیگنالی وجود ندارد؛ هر عددی آنجا ساختگی بود. به‌جایش با فرهنگ تلفظ **جلویش گرفته می‌شود** و کلمه‌هایی که تلفظشان را نداریم به فروشگاه گزارش می‌شود.

> **Lip Sync عمداً اینجا نیست.** ویدیوهای فعلی گوینده‌ی روی تصویر ندارند. فقط اگر «ویدیو با presenter» وارد محصول شود، Lip Sync و Viseme Mapping فاز جدا می‌گیرند.

**DoD:** صدای تولیدشده قبل از Final Render نمره می‌گیرد و زیر آستانه دوباره تولید می‌شود؛ حالت `Local Only` واقعاً بدون اینترنت کار می‌کند.

> **تله‌ی Proxy این است که دو فایل سر زمان با هم اختلاف پیدا کنند.** اگر نسخه‌ی پیش‌نمایش نرخ فریم متفاوتی داشته باشد، برشی در ثانیه‌ی ۱۲.۴ روی هر کدام به فریم دیگری می‌افتد — و ویدیوی خروجی به‌شکلی نامحسوس با آنچه فروشگاه تأیید کرده فرق می‌کند، و این تفاوت فقط در رندر نهایی معلوم می‌شود. پس نرخ فریم **عمداً دست‌نخورده** می‌ماند؛ فقط وضوح کم می‌شود.
>
> و اگر ویدیو از قبل کوچک باشد، پیش‌نمایش **رد می‌شود**: یک کلیپ 640×360 بعد از رمزگذاری دوباره ۱.۴ برابر **بزرگ‌تر** درآمد و یک رندر هم خرج برداشت.
>
> **دو قطعه در یک لحظه روی یک ترک، ادیت نیست.** ترک یک لایه است، پس جواب تعریف‌شده‌ای ندارد که کدام دیده شود — و رندرکننده‌ای که ازش بپرسی، بی‌صدا یکی را انتخاب می‌کند. به‌جایش نام هر دو قطعه گفته می‌شود.
- [x] زیرنویس خودکار — خط‌به‌خط از روی نریشن، و **کلمه‌به‌کلمه** با ویسپر
- [x] زیرنویس ویدیوی آپلودی مشتری — `transcribe_upload_task`
- [x] کلید **روشن/خاموش** برای هر ویدیو، با پیش‌فرض فروشگاه — و انتخاب «روی تصویر بسوزد یا فایل جدا»
- [x] زوم روی چهره و جای هوشمند زیرنویس — `services/video/faces.py`

>
> آنچه **واقعاً** نامعلوم است، زمان است — و آن از خود موج خوانده می‌شود: همان پوشش صدایی که QC اندازه می‌گیرد، مکث‌های داخل نریشن را پیدا می‌کند و مرز خطوط روی آن‌ها می‌نشیند. وقتی صدا خوانده نشود، از روی طول متن تخمین می‌زند و **در خروجی می‌گوید که تخمین زده** — تخمینی که خودش را اندازه‌گیری جا بزند، زیرنویسی می‌شود که جلو و عقب می‌رود و کسی نمی‌فهمد چرا.
- [x] B-Roll — `services/video/broll.py`

> **از عکس‌های خود فروشگاه، هرگز از تصویر استوک.** عکس استوکِ یک کفش عمومی در ویدیویی که *این* کفش را می‌فروشد، واضح‌ترین علامت این است که کسی حواسش نبوده — دقیقاً همان تصور «AI slop» که بقیه‌ی محصول برای فرار از آن ساخته شده.
>
> **بیشتر اوقات رد می‌کند.** دوربین در حرکت؟ تصویر خودش چیزی برای دیدن دارد. ویدیوی ساکت؟ تصویر کمکی روی سکوت، فقط سکوت است با عکس. بخش‌های کوتاهِ حرف‌زدن؟ بریدن به آن نمی‌ارزد. و سقف `MAX_SHARE` نمی‌گذارد بیش از یک‌سوم ویدیو پوشیده شود، چون آن دیگر اسلایدشو است با صدای راوی.

> **سه‌حالته است، نه دوحالته.** `None` روی ویدیو یعنی «هرچه فروشگاه تصمیم گرفته»، و همین است که کلید فی‌الویدیو را قابل‌استفاده می‌کند: فروشگاه یک بار پیش‌فرض را می‌گذارد و فقط آن‌هایی را دست می‌زند که فرق دارند. کلید دوحالته، روی **هر** ویدیو یک تصمیم تحمیل می‌کند، و آدم‌ها به چنین تصمیم‌هایی با پذیرفتن هرچه جلویشان است جواب می‌دهند.
>
> **مدل هرگز حرف ما را عوض نمی‌کند.** برای ویدیویی که خودمان ساخته‌ایم، ویسپر فقط برای **زمان** استفاده می‌شود و رونویسی‌اش دور ریخته می‌شود — متن ما از اول درست است، و «نایکی»ای که مدل بد شنیده ولی سر ثانیه‌ی درست نشسته، از رونویسی‌ای که باید تصحیحش کنیم ارزشمندتر است.
>
> **برای ویدیوی مشتری برعکس:** آنجا کلمه‌ها واقعاً نامعلوم‌اند، پس خطی که با اطمینان پایین شنیده شده **علامت می‌خورد** نه اینکه صاف شود. فروشگاه‌دار می‌تواند کلمه‌ی غلط را درست کند؛ خطی را که بی‌صدا حذف کرده‌ایم نمی‌تواند.

> **چیزی که کد تصمیم نمی‌گیرد، مدل هم دستش به آن نمی‌رسد.** مدل فقط `{tool, params, reason}` می‌نویسد و هر سه از `validate` رد می‌شوند: ابزار ناشناخته و پارامتر ناشناخته **رد** می‌شوند، عدد خارج از بازه **محدود** می‌شود و محدودشدنش روی خود عملیات نوشته می‌شود تا در برنامه‌ای که آدم تأیید می‌کند دیده شود.
>
> **یک باگ واقعی که تست گرفت:** روی ویدیویی که میکروفنش ضبط نکرده بود، «حذف سکوت» یعنی «حذف کل ویدیو». حالا `no_speech` جدا تشخیص داده می‌شود و پیشنهاد حذف سکوت را کلاً خاموش می‌کند، و `render` هم زیر یک ثانیه خروجی نمی‌دهد.

> **بازبینی کیفیت تدوین و بینایی ماشین (۱۴۰۵/۰۶/۳۰).** یک بازبینی
> سه‌لنزی (سنجش بینایی، حلقه‌ی تصمیم، رندر ffmpeg) با تأیید مستقل دو داور،
> همه با اجرای واقعی ffmpeg روی کلیپ‌های مصنوعی و بدون GPU. آنچه پیدا و
> درست شد — هر مورد با اندازه‌گیری، نه حدس:
>
> - **زوم آرام کل رندر را می‌شکست** (`crop` گزینه‌ی `enable` ندارد) → حالا
>   `zoompan` با رمپ نرم، لنگر روی چهره و زمان مبدأ (`it`)؛ با مرجع Pillow
>   تطبیق شد (اختلاف ۲ از ۲۵۵).
> - **نمونه‌گیری فریم فقط ۳–۴ ثانیه‌ی اول را می‌دید**؛ حالا در کل کلیپ و
>   شامل فریم آخر. چهره‌ها روی ۵۱۲px، مدل بینایی روی ۶۴۰px با عکس محصول
>   هم‌اندازه.
> - **نوردهی با میانگین سنجیده می‌شد**: محصول روی سفید «سوخته» و روی مشکی
>   «تاریک» و اصلاح خودکار خرابش می‌کرد → درصدی (p5/p50/p95 + کسر کلیپ).
> - **رنگ‌زدگی روی کل فریم**: محصول نارنجی «رنگ‌زده» → فقط روی پیکسل‌های
>   خنثی؛ و `colorbalance` در این بیلد **هیچ اثری** نداشت (۱۶۲/۱۳۹/۱۱۷ →
>   ۱۶۲/۱۳۸/۱۱۶) → `colorchannelmixer` با ضریب از رنگ خنثی‌ها (۴۴ → ۱).
> - **لرزش = حرکت** بود؛ حالا `frame_stats.camera_shake` (phaseCorrelate،
>   باقیمانده‌ی مسیر نرم): پن ۰.۰۰۲، لرزش واقعی ۰.۰۲–۰.۰۳. فلیکر/فریز/سیاهی/

>   تاریکی، نه آفست)؛ تعمیر فقط اگر محورش ≥۸ بهتر شود می‌ماند؛ بازبینی
>   بعد از تعمیر محورهای بینایی را نگه می‌دارد (قبلاً ۷۷ → ۱۰۰ می‌شد).
> - **بازتولید یک قطعه**: در حالت خودکار تا `SEGMENT_AUTO_ATTEMPTS` تلاش با
>   پرامپت اصلاح‌شده و seed تازه، بهترین نسخه نگه داشته می‌شود، اعتبار از
>   زنجیره‌ی `credits.reserve_retry`؛ در حالت Safe دکمه‌ی «دوباره بساز»
>   (`POST /jobs/{id}/regenerate/`) با انتخاب علت. `_should_pause` روی
>   verdict می‌ایستد نه ۰.۶ ناسازگار؛ بدون مدل بینایی یک بار در هر کار می‌پرسد.
> - **کامپایلر پرامپت**: `scene_state.compile_prompt` (لنگرهای کیفیت،
>   negative ویدیویی، راهنمای هر علت، بودجه‌ی کلمه). **SceneState عملاً خالی
>   بود** چون پرامپت سناریو هرگز `state` نمی‌خواست → v4 می‌خواهد؛ از محصول

> - **گذار کل ویدیو را سیاه می‌کرد**، fade-out با پیش‌فرض ۰ از ثانیه‌ی ۰.۴
>   سیاه می‌کرد، **تثبیت هیچ‌وقت اجرا نمی‌شد** (دونقطه‌ی مسیر ویندوز، بدون
>   `input=`)، speed صدا را ناهمگام می‌کرد و با برش لغو می‌شد، `%` در

> **دو قانونی که شکل این بخش را تعیین کرد:**
>
> **انتساب یک‌بار نوشته می‌شود و دیگر عوض نمی‌شود.** فروشگاهی که در خرداد با کد معرفی آمده، در اسفند هم با کد معرفی آمده — حتی بعد از اینکه آن کد پاک شده باشد. گزارشی که انتساب را از ردیف‌های زنده دوباره حساب کند، هر بار که کسی چیزی را مرتب می‌کند تاریخ خودش را بازنویسی می‌کند، و عددی که خودبه‌خود جابه‌جا می‌شود عددی است که کسی به آن تکیه نمی‌کند.
>
> **هیچ پولی از اینجا پرداخت نمی‌شود.** `Reward` می‌نویسد چقدر و به چه کسی بدهکاریم؛ پرداختش کار یک آدم است. خط لوله‌ی پرداخت خودکار روی رویداد ثبت‌نام یک سطح حمله‌ی تقلب است که راه جبرانش پس‌گرفتن پول از مشتری است.
>
> **یک باگ واقعی که تست معماری گرفت:** کد معرفی روی `request.user` کلید خورده بود، پس فروشگاهی با دو مدیر دو کد می‌گرفت، آمار معرفی‌اش بین آن دو تقسیم می‌شد و پاداش به کسی می‌رسید که زودتر کلیک کرده بود. حالا کد مال **فروشگاه** است و پاداش به حسابی می‌رسد که پول را می‌دهد.

**DoD:** داشبورد بگوید هر مشتری از کجا آمده و کدام کانال ROI بهتری داشته.

>
> **ترند تاریخ مصرف دارد.** هر ردیف ساعت دیده‌شدنش را دارد و بعد از ۳۶ ساعت «کهنه» است — و کهنه که شد، دکمه‌ی «بساز» رد می‌کند، چون فروشگاه‌دار دارد ثانیه‌ی GPU خرج لحظه‌ای می‌کند که گذشته است.

* product appearance
* colors

* camera perspective
* lighting
* scene style
* composition
* visual semantics
* motion continuity

SEGMENT N

generate a new visual anchor when required.
