## ۱. شکل کلی

یک **کارمند فروش و مارکتینگ AI** برای فروشگاه آنلاین: فروشگاه و کاتالوگ →
هوش محصول و بازار → چت فروش → تولید محتوا (پوستر، عکس محصول، کپشن، ویدیوی
صحنه‌بندی‌شده با صدا) → تأیید → انتشار → آمار.

```
React (Vite + TS + Tailwind)  ──────── REST ────────►  Django + DRF
      (پیشرفت کار با SSE؛ polling جایگزین است)
                                                          │
                              ┌────────────── لایه‌ی سرویس (هیچ منطقی در ویو)
                              │
        ┌──────────┬──────────┼──────────────┬───────────────┐
        ▼          ▼          ▼              ▼               ▼
    دیتابیس     Redis      Celery       گیت‌وی AI        ذخیره‌ی مدیا
   SQLite/PG                  │             │            (لوکال → آماده‌ی S3)
                      صف کار GPU      ┌─────┴─────┐
                    (هم‌زمانی = ۱)     ▼           ▼
                                    Ollama      ComfyUI
                                  qwq / vl    FLUX / Wan 2.2
                                                   │
                                              FFmpeg / TTS
                                                   │
                                     n8n / نوین‌هاب → شبکه‌های اجتماعی
```

## ۲. هشت قاعده

۱. **هیچ منطق کسب‌وکاری در ویو نیست** — ویو اعتبارسنجی و اجازه می‌دهد؛ کار را سرویس می‌کند.
۲. **هر فراخوانی AI از گیت‌وی رد می‌شود** — هیچ `requests.post` مستقیمی به Ollama یا ComfyUI در کد اپ‌ها نیست. گیت‌وی بدون `store` کار نمی‌کند، و همین است که جلوی رفتن داده‌ی یک فروشگاه به API بیرونی بدون اجازه‌اش را می‌گیرد.
۳. **هر تولید سنگین در Celery است** — درخواست HTTP هرگز پشت GPU نمی‌ماند.
۴. **GPU منبع کمیاب است** — صف اختصاصی با هم‌زمانی ۱ (`GPU_CONCURRENCY_LIMIT`).
۵. **هیچ فایل تولیدشده‌ای بدون ردیف دیتابیس نیست** — نام فایل UUID است، نه ورودی کاربر.
۶. **ایزوله‌سازی مستأجر در کوئری و دسترسی است** — هرگز فقط در فرانت.
۷. **پیکربندی از محیط می‌آید** — `OLLAMA_BASE_URL`، `COMFYUI_BASE_URL`، `REDIS_URL`، `N8N_WEBHOOK_URL`، `GPU_CONCURRENCY_LIMIT`، `VIDEO_SEGMENT_DURATION`، `TTS_PROVIDER` و نام مدل‌ها.
۸. **خروجی AI ساختاریافته است** — طرح JSON برای هر قابلیت، اعتبارسنجی + ترمیم + تلاش دوباره. هیچ‌جا نثر آزاد برای تصمیم ماشینی پارس نمی‌شود.

## ۳. لایه‌ی AI

### انتزاع ارائه‌دهنده

```
گیت‌وی (services/ai/gateway.py)
 ├── LLMProvider      متن        → Ollama | API سازگار با OpenAI
 ├── VisionProvider   بینایی     → Ollama (qwen3-vl) | API
 ├── ImageProvider    تصویر      → ComfyUI (FLUX) | API
 ├── VideoProvider    ویدیو      → ComfyUI (Wan 2.2) | API
 └── TTSProvider      صدا        → edge-tts (پیش‌فرض) | gTTS (بدون فارسی)
```

ارائه‌دهنده‌ها **پیکربندی می‌شوند، هاردکد نیستند** — عوض کردن مدل یا افزودن
یک سرویس ابری نباید به منطق کسب‌وکار دست بزند. هر قابلیت (متن/بینایی/تصویر/
ویدیو) جداگانه بین لوکال و API سوییچ می‌شود؛ API شدنِ ویدیو، ComfyUI را برای
تصویر نمی‌خواباند.

### مسیریابی مدل

| کار | مدل | نکته |
|---|---|---|
| استدلال، استراتژی، سناریو، صحنه‌بندی، مدیریت اعتراض | `qwq:32b` | «مغز». خروجی در طرح JSON سفت‌وسخت پیچیده می‌شود — QwQ بلوک `<think>` می‌ریزد که باید قبل از پارس جدا شود |
| تحلیل عکس محصول، اعتبارسنجی تصویر تولیدی | `qwen3-vl:30b` | |
| کارهای کدی داخلی | `qwen3-coder:30b` | **نه** برای متن بازاریابی |
| تولید و ادیت تصویر | FLUX.1-dev FP8 روی ComfyUI | |
| قطعه‌ی ویدیو i2v | Wan 2.2 (نویز بالا → نویز پایین) + LoRA lightx2v | |

### چرخه‌ی یک درخواست

```
فراخوان → گیت‌وی: آیا سیاست داده‌ی این فروشگاه اجازه می‌دهد؟
  → نه → PolicyBlocked (نه fallback بی‌صدا)
  → بله → نسخه‌ی پرامپت + مدل از رجیستری
  → رندر پرامپت → فراخوانی ارائه‌دهنده (تایم‌اوت، تلاش دوباره با backoff)
  → جدا کردن <think>…</think>
  → پارس JSON → اعتبارسنجی با طرح
      شکست: یک ترمیم کنترل‌شده → یک تلاش ساختاریافته → FAILED
  → ثبت AIRequest + AIResponse (مدل، نسخه‌ی پرامپت، تأخیر، نتیجه)
  → نتیجه‌ی تایپ‌دار
```

تایم‌اوت متن ۶۰۰ ثانیه (لود سرد مدل ۳۲B زمان می‌برد)، دو تلاش، backoff
نمایی. بودجه‌ی کانتکست `OLLAMA_NUM_CTX` (پیش‌فرض ۸۱۹۲) — گیت‌وی ورودی را
کوتاه یا خلاصه می‌کند، هرگز بی‌صدا سرریز نمی‌شود.

### رجیستری پرامپت

هر قابلیت یک پرامپت نسخه‌دار دارد در `services/ai/prompts/`، و هر ردیف
`AIRequest` می‌نویسد کدام نسخه اجرا شده. ویرایش پرامپت = نسخه‌ی جدید، نه
تغییر در جا.

### خط‌های اصلی

**هوش محصول:** داده + عکس‌ها → `qwen3-vl` (تحلیل هر عکس، ساختاریافته) →
`qwq` (سنتز استراتژی) → `ProductIntelligence`. داده‌ی کاربر، استنتاج مدل و
ریسرچ بیرونی **جدا از هم** ذخیره و برچسب می‌خورند.

**ایجنت فروش:** پیام → تشخیص نیت → **خواندن قیمت/موجودی از دیتابیس** →
پاسخ فقط بر پایه‌ی همان → اکشن. قاعده‌ی سفت: مدل قالب‌بندی می‌کند، هرگز
نمی‌سازد. پایین‌تر از آستانه‌ی اطمینان یا حساس به سیاست → تحویل به انسان.

**استودیوی تصویر:** محصول + عکس مبنا → تحلیل بینایی → جهت‌دهی خلاقانه →
ComfyUI (ورک‌فلوی نسخه‌دار) → اعتبارسنجی اختیاری با بینایی (محصول حفظ شده؟)
→ ردیف دیتابیس. دو حالتِ جدا: **حفظ محصول** در برابر **ترکیب خلاقانه** —
ورک‌فلوی متفاوت، سخت‌گیری متفاوت.

### لایه‌ی ComfyUI

`services/comfyui/`:

- `client.py` — آپلود تصویر، ارسال گراف (`POST /prompt`)، پیگیری با نظرسنجی
  `‎/history/{id}`، دریافت خروجی (`GET /view`). **وب‌سوکت لازم نشد:** یک رندر
  چند دقیقه طول می‌کشد، پس نظرسنجی هر ۲ ثانیه هزینه‌ای ندارد و یک وابستگی کم
  می‌کند.
- `workflows/` — سه گراف نسخه‌دار در **قالب API**: `wan22_i2v_v1`،
  `flux_txt2img_v1`، `flux_img_edit_v1`. هرکدام یک manifest دارد که
  **ورودی‌های قابل وصله** را نام می‌برد (تصویر، مثبت، منفی، پیشوند نام، seed،
  ابعاد) — تا شناسه‌ی نودها فقط در یک جا زندگی کند. نسخه‌ی UI-format اصلی در
  `ui_reference/` نگه داشته شده.

### مدیریت GPU

صف `gpu` با هم‌زمانی ۱؛ کارهای فقط-Ollama روی صف `ai` جدا. خط‌های طولانی
(ویدیو) جای GPU را **به‌ازای هر قطعه** می‌گیرند نه کل کمپین، تا کارهای کوچک
بتوانند لای آن بروند. فشار VRAM بین Ollama 30B و ComfyUI با آنلود کردن مدل
(`keep_alive: 0`) قبل از مرحله‌های سنگین حل می‌شود — `services/gpu.py`.

## ۴. خط تولید ویدیو

تیزر بلندتر از یک تولید Wan، از **قطعه‌های ۵ ثانیه‌ای** ساخته می‌شود که با
لنگر فریم آخر به هم زنجیر می‌شوند.

```
هوش محصول → کانسپت و سناریو (ساختاریافته)
 → صحنه‌بندی: N صحنه × ~۵ ثانیه، هرکدام با
   {ایندکس، مدت، پرامپت بصری، پرامپت حرکت، نریشن، نوع ترنزیشن}
 → حلقه‌ی قطعه (Celery، صف gpu):
     تصویر لنگر → Wan 2.2 → کلیپ ۵ ثانیه → استخراج فریم آخر
 → کنترل کیفیت → اتصال با FFmpeg → نریشن TTS → هم‌ترازی → میکس → MP4
```

مدت قطعه و طول کل پیکربندی‌شدنی‌اند (`VIDEO_SEGMENT_DURATION`، پیش‌فرض ۵) —
هیچ‌جا ۳۰ ثانیه هاردکد نیست.

### مدل پیوستگی

| نوع ترنزیشن | لنگر این قطعه |
|---|---|
| `CONTINUE` | فریم آخر قطعه‌ی قبلی (پیش‌فرض) |
| `TRANSITION` | فریم آخر قبلی + پرامپت حرکتِ آگاه به گذار |
| `NEW_SCENE` | تصویر تازه‌ی FLUX — فقط وقتی کاتِ سخت لازم است یا فریم قبلی غیرقابل‌استفاده |

- **به‌صورت پیش‌فرض FLUX برای هر قطعه اجرا نمی‌شود** — پیوستگی را نابود می‌کند.
- لنگر قطعه‌ی اول: تصویر FLUX از پرامپت بصری صحنه‌ی یک، اختیاراً با عکس واقعی
  محصول به‌عنوان مبنا (ورک‌فلوی img-edit).
- برای هر قطعه **ثبت می‌شود** لنگرش کدام تصویر/فریم بود — هم برای حسابرسی، هم
  برای از سرگیری.
- **حافظه‌ی صحنه:** فریم آخر فقط یک لحظه را حمل می‌کند. هشت محور دیگر هم
  منتقل می‌شوند (شخصیت، اشیا، مکان، نور، دوربین، لباس، رنگ، اکشن) و
  **سکوت یعنی «مثل قبل» نه reset** — همین یک تصمیم جلوی عوض شدن رنگ کاپشن
  وسط ویدیو را می‌گیرد. کاتِ عمدی هیچ چیز منتقل نمی‌کند.

### از سرگیری

یک کار والد به‌ازای هر ویدیو؛ گام‌های فرزند: سناریو → صحنه‌بندی → قطعه[i] →
اتصال → صدا → میکس → نهایی‌سازی.

**قاعده‌ی از سرگیری:** قطعه‌ی شکست‌خورده تنهایی تلاش دوباره می‌کند؛ قطعه‌های
تمام‌شده **هرگز** بازتولید نمی‌شوند. از سرگیری از اولین گام غیر-DONE با
لنگرهای ذخیره‌شده ادامه می‌دهد.

پیشرفت از حالت واقعی کار می‌آید — **هیچ درصد ساختگی‌ای نیست**.

### استخراج فریم و اتصال

```
ffmpeg -sseof -0.1 -i segment_i.mp4 -frames:v 1 -q:v 1 anchor_{i+1}.png
```

قطعه‌ها با عرض/ارتفاع/FPS/کدک یکسان تولید می‌شوند (ورک‌فلو تضمینش می‌کند)، پس
اتصال بدون رمزگذاری دوباره انجام می‌شود:

```
ffmpeg -f concat -safe 0 -i list.txt -c copy combined.mp4
```

اگر پارامترها نخواندند، `filter_complex` با رمزگذاری دوباره جایگزین است.

### صدا با آگاهی از زمان

```
نریشن هر صحنه → TTS → صدای هر صحنه
 → اندازه‌گیری مدت واقعی (ffprobe)
 → هم‌ترازی: صدای i باید در پنجره‌ی صحنه‌ی i جا شود
     بلند بود → ۱) کوتاه کردن نریشن و تولید دوباره
                ۲) یا atempo در بازه‌ی ۰.۹ تا ۱.۱
                ۳) یا جابه‌جایی مرز صحنه اگر طراحی اجازه بدهد
 → اتصال صداها با سکوتِ پرکننده تا مرز صحنه‌ها
 → میکس روی ویدیو
```

**هرگز نریشن وسط جمله قطع نمی‌شود؛ هرگز یک فایل صوتی ناهمگام روی کل ویدیو
نمی‌افتد.**

TTS یک رابط است (`TTS_PROVIDER`). پیش‌فرض **edge-tts** با صدای فارسی
`fa-IR-FaridNeural` که واقعاً تست شده. gTTS به‌عنوان جایگزین مانده ولی
**فارسی ندارد** و زبانش را از اول اعتبارسنجی می‌کند.

## ۵. خطا، لاگ، امنیت

**خطا:** هر سرویس بیرونی (Ollama، ComfyUI، Redis، n8n، TTS، ذخیره‌سازی)
تایم‌اوت، تلاش دوباره‌ی کران‌دار با backoff، استثنای تایپ‌دار، حالت `FAILED`
با متن خطای ذخیره‌شده، و پیام ساده برای کاربر دارد. **تلاش بی‌نهایت نیست؛
fallback بی‌صدا به داده‌ی جعلی هم نیست.**

**لاگ:** ساختاریافته (JSON در production) با شناسه‌ی درخواست، کاربر، فروشگاه،
کار، مدل، نسخه‌ی ورک‌فلو، مدت و نتیجه. جدول‌های `AIRequest`/`AIResponse` هر
فراخوانی AI را نگه می‌دارند. **هیچ‌وقت راز لاگ نمی‌شود.**

**امنیت:** JWT، بررسی دسترسی روی هر شیء، اعتبارسنجی آپلود (نوع/حجم/نام)، نام
فایل UUID، مدیا به‌تفکیک مستأجر، رازها در `.env`، CORS صریح، محدودیت نرخ روی
اندپوینت‌های AI، و توکن روی وب‌هوک n8n.

### ریسک‌های بازِ امروز

۱. **کیفیت خروجی** — اینکه Wan 2.2 و FLUX روی این سخت‌افزار محتوای
   **قابل‌فروش** بدهند، با هیچ تستی معلوم نمی‌شود. تنها راهش اجرای واقعی است:
   [`../test.md`](../test.md).
۲. **زمان تولید** — یک ویدیوی ۳۰ ثانیه‌ای یعنی ۶ قطعه. رابط باید صادقانه
   بگوید چقدر طول می‌کشد، و بازه‌ی ۳ تا ۹ دقیقه بر ثانیه فاصله‌ی بین
   کسب‌وکاری است که کار می‌کند و یکی که نمی‌کند.
۳. **کیفیت پیوستگی** — لنگر فریم آخر بعد از چند قطعه افت می‌کند؛ صحنه‌بند
   باید بداند کِی لنگر تازه لازم است.
۴. **اتکاپذیری خروجی ساختاریافته** — مدل استدلالی پرحرفی می‌کند؛ طرح JSON +
   ترمیم + تلاش دوباره اجباری است.
۵. **فشار VRAM** — Ollama 30B و ComfyUI سر یک کارت. آنلود خودکار هست ولی
   روی سخت‌افزار واقعی اندازه‌گیری نشده.
