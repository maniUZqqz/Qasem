# روانیِ ویرایشگرِ دستیِ ویدیو — دورِ ۲ (۱۴۰۵/۰۸/۲۳)

مالک: «ادیتور خیلی خیلی کند و لَگی است». علتِ اصلی: **هر تیکِ پخش (~۱۴ بار در ثانیه) و هر حرکتِ ماوس هنگامِ جست‌وجو/کشیدن کلِ فضای کار را دوباره می‌ساخت**
(سطلِ رسانه، مانیتور، بازرس، نوارِ برش، تایم‌لاین و همهٔ قطعه‌ها)، چون «زمانِ سرِ پخش» یک `useState` در `VideoWorkspace` بود.

## اعداد (مرورگرِ واقعی روی گرافیکِ مجتمعِ قدیمی، فروشگاهِ ۳۴ آزمایشی، ۲۶ قطعه، ۳ ویدیو؛ «قبل» = همان کد + فقط شمارنده‌ها)

رایانهٔ آزمون هم‌زمان کارِ دیگران را هم می‌کرد؛ اعدادِ زمانی ±۳۰٪ نوسان دارند، **شمارِ رندرها دقیق‌اند**.

**شمارِ رندر در ۶ ثانیه پخش** (قطعه انتخاب، تبِ «رنگ»، بخشِ «حالت‌ها» باز، اسکوپ باز، ویدیوی واقعی):

| بخش | قبل | بعد |
|-----|-----|-----|
| کلِ فضای کار (`Workspace`) | ۱۶۵ | **۱** |
| سطل، بازرس، نوارِ برش، تایم‌لاین، پنلِ رنگ (هرکدام) | ۱۱۸ | **۰** |
| تصویرِ کوچکِ حالت‌ها (`lookThumbBuild`) | ۱۱۸ | **۰** (هنگامِ پخش) |
| برداشتن/گذاشتنِ گوشِ کیبورد (`keydownSubscribe`) | ۱۱۸ | **۰** (یک بار در آغاز) |
| مانیتور | ۱۳۶ | ۹۶ (یک بار در هر تیک؛ لازم است) |

مشغولیِ رشتهٔ اصلی در همین ۶ ثانیه ۹۷٪ ← ۸۴٪، فریم‌بر‌ثانیه ۳۵ ← ۴۰.

**هزینهٔ خالصِ ری‌اکت** (فایلِ ویدیو سرو نمی‌شود، همان سناریو؛ میانهٔ ۳ اجرا): جاوااسکریپتِ ۶ ثانیه پخش **۲۱۱۶ ← ۷۲۴ms (−۶۶٪)**، زمانِ رشتهٔ اصلی ۴۳۰۱ ← ۳۲۱۴ms، فریم‌های بالای ۵۰ms ۵۶ ← ۲۰. بدونِ اسکوپ/پنلِ رنگ: ۹۵۱ ← ۵۰۷ms جاوااسکریپت (−۴۷٪)، مشغولیِ رشتهٔ اصلی ۵۲٪ ← ۲۹٪.

**جست‌وجوی روی خطِ زمان** (۹۰ گام، رویدادِ ساختگیِ درون‌صفحه؛ میانهٔ ۳ اجرا): جاوااسکریپت در هر گام ۱۱٫۴ ← ۵٫۸ms (−۴۹٪)، رندرِ فضای کار ۱۰۱ ← ۰، سطل/بازرس/نوارِ برش/تایم‌لاین ۸۹ ← ۰. موقعیتِ خطِ سرِ پخش در هر دو یکی است.

**کشیدنِ یک قطعه** (چسبیدن خاموش، ۹۰ گام): پردازنده در هر گام ۱۴٫۵ ← ۸٫۲ms (−۴۳٪)، جاوااسکریپت ۵٫۸ ← ۳٫۳ms؛ گذرِ رندرِ بازرس/نوارِ برش/تایم‌لاین ۸۹ ← ۴۵؛ رندرِ قطعه‌ها (`ClipView`) ۵۲۵ ← ۴۶. هر دو ۴۰ مکانِ متفاوت را برای قطعه می‌بینند (یعنی دیده‌شدنِ حرکت همان است).

**ماشینِ ضعیف** (پردازنده ۴ برابر کندتر، پخشِ سنگین با اسکوپ): فریم‌بر‌ثانیه ۲۹ ← ۳۶؛ در پخشِ ساده فریم‌های بالای ۵۰ms ۱۵ ← ۳ و طولانی‌ترین توقفِ رشتهٔ اصلی ۶۸۳ ← ۱۲۲ms.

**ثبتِ تاریخچه** (۳۰۰ قطعه): بررسیِ «تغییری شد؟» ۱٫۴۳ms ← ۹µs (×۱۶۰)؛ `JSON.stringify` از کلِ پروژه برای هر ثبت ۲ ← ۰.

**بارِ اول:** جاوااسکریپتِ ورودِ پنل ۳٫۵۶ مگابایت (۱٫۱۰ فشرده) ← **۱٫۵۷ مگابایت (۰٫۴۷ فشرده)**؛ فضای کارِ ویرایش ۵۷۰ کیلوبایتِ جدا (۲۰۸ فشرده، فقط حالتِ «دستی»)، ویرایشگرِ عکس ۶۶۲ کیلوبایتِ جدا، three.js ۷۲۹ کیلوبایتِ جدا (فقط صفحه‌های سه‌بعدی). در آزمونِ ما (از راهِ تونلِ SSH): «فضای کار دیده می‌شود» ۸٫۱ ← ۵٫۵ ثانیه.

**درستیِ رفتار:** ۵۵ گامِ میان‌بر/ویرایش (جست‌وجو، ورودی/خروجی، نشانگر، کپی/چسباندن/تکرار/حذف، ابزارها، متن، جابه‌جاییِ فریمی، برش، J/K/L، Space، راهنما، جستجوی ابزار، برگشت/جلو) روی نسخهٔ قبل و بعد **عیناً یک وضعیتِ صفحه** می‌دهند (فقط ساعتِ پخشِ واقعی فرق دارد)؛ ذخیرهٔ خودکار با هر گامِ ثبت‌شده یک بار PUT می‌زند و با برگشت/جلو همراه می‌شود.

هنوز بزرگ‌ترین هزینهٔ پخش/جست‌وجو **خودِ ترکیبِ تصویر** است (`Compositor`: `drawImage` از ویدیو روی بومِ ۲بعدیِ پردازنده‌ای؛ روی گرافیکِ مجتمعِ قدیمی ~۳٬۰۰۰ms از ۶ ثانیه). ریاکت دیگر مشکلِ اصلی نیست.

**بازآزمایی پس از ادغام با نسخهٔ زندهٔ همان روز** (همان مرورگر/سناریو؛ «قبل» = ساختِ بدونِ تغییر + فقط شمارنده‌ها): شمارِ رندر در ~۷ ثانیه پخش: `Workspace` ۱۴۰ ← **۱**، `Bin/Inspector/TrimBar/TimelineView/ColorPanel` هرکدام ۹۹ ← **۰**، `lookThumbBuild` ۹۹ ← **۰**، `keydownSubscribe` ۹۹ ← **۱**؛ فریم‌بر‌ثانیه ۲۴ ← ۴۸ و فریم‌های بالای ۵۰ms ۶۲ ← ۰. آزمونِ کاربردی روی ساختِ تازه: تقسیمِ قطعه با `S` (۲۶ ← ۲۷)، برگشت (۲۶)، جلو (۲۷)، حذف + برگشت، نشانگر `M` + برگشت، Space/پخش/جست‌وجو، Home/فلش، راهنمای `?` — همان نتیجهٔ ساختِ قبل؛ ذخیرهٔ خودکار برای هر گام (تقسیم، برگشت، جلو) دقیقاً یک `PUT`. تست‌های واحد (۹ فایل)، `tsc` و ۱۴۴ تستِ بک‌اندِ ویرایشگر سبز.

## قاعده برای کدهای بعدی

* «زمانِ سرِ پخش» را **هرگز** `useState` در فضای کار نکنید. در رویداد: `ph.get()` (در `VideoWorkspace`) یا `usePlayheadStore().get()`. برای نمایش: `usePlayhead()` / `useThrottledPlayhead(ms)` فقط در کوچک‌ترین کامپوننتی که زمان را نشان می‌دهد. `wsApi.time` یک getter است.
* به فرزندِ `memo` callbackِ inline ندهید؛ `useEvent`/`useStableFns`/`useCallback`؛ JSX را `useMemo` کنید.
* هر چیزِ تازه‌ای که در هر تیک کار می‌کند، با `countRender("نام")` شمرده شود (در حالتِ عادی هزینه‌ای ندارد).

## سنجش

* در کنسول یا آزمونِ مرورگر پیش از بارِ صفحه `window.__nmPerf = {}` بگذارید؛ شمارنده‌ها در `window.__nmPerf[نام]` جمع می‌شوند (`Workspace`, `Monitor`, `Inspector`, `Bin`, `TimelineView`, `ClipView`, `TrimBar`, `ColorPanel`, `lookThumbBuild`, `mixerTick`, `cropPaint`, `historyPush`, `historyStringify`, `keydownSubscribe`).
* `docs/editor-perf/probe.py`: آزمونِ Playwright (پخش، جست‌وجو، کشیدن، میان‌برها + ذخیرهٔ خودکار + برگشت/جلو). فقط روی **نسخهٔ آزمایشیِ** سایت با کاربرِ آزمایشی (`NM_PROBE_BASE`, `NM_PROBE_USER`, `NM_PROBE_PASS`). با `NOMEDIA=1` فایل‌های ویدیو سرو نمی‌شوند تا فقط هزینهٔ ری‌اکت سنجیده شود؛ سناریوی `ip` رویدادِ ساختگیِ درون‌صفحه می‌فرستد (بدونِ تأخیرِ ابزار).
* آزمونِ واحد: `cd frontend && node_modules/.bin/esbuild tests/editor-perf.test.ts --bundle --platform=node --format=esm --outfile=/tmp/editor-perf.test.mjs && node /tmp/editor-perf.test.mjs`
  (۲۰٬۰۰۰ جفتِ تصادفی: `jsonEqual` ≡ `JSON.stringify`؛ انبارِ سرِ پخش؛ شمارنده).

## کارهای بعدی (انجام نشد)

* `Compositor`: مسیرِ WebGL یا وضوحِ کمتر هنگامِ پخش (بزرگ‌ترین هزینهٔ باقی‌مانده)؛ رسمِ دوباره فقط وقتی فریمِ منبع واقعاً عوض شد (ویدیوی ۳۰fps روی نمایشگرِ ۶۰Hz).
* خوانشِ پیکسلِ اسکوپ‌ها (`getImageData`) روی گرافیکِ ضعیف؛ می‌شود نرخش را هنگامِ پخش کم کرد.
* ویرایشگرِ آهنگ/گروه‌های دیگرِ پنل (رشد، استودیو، سرورهای پردازش) هم با `lazyPage` جدا بشوند.
